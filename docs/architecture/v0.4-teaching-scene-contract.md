## 1. Purpose

This specification defines `TeachingScene` as the canonical, versioned, renderer-safe, learner-facing content contract consumed by the Classroom Display.

`TeachingScene` MUST be:

- generated or assembled as structured data;
- validated before publication;
- safe for deterministic rendering;
- independent from a specific frontend framework or rendering library;
- compatible with atomic scene publication;
- compatible with prepared-lesson caching;
- compatible with degraded connectivity;
- compatible with public/private projection boundaries.

The renderer owns final presentation behavior. The AI MUST NEVER generate renderer code, layout instructions, styling, animation, or executable display logic.

This document does not define:

- frontend frameworks, rendering libraries, or styling technologies;
- serialization formats or transport protocols;
- production code or framework manifests;
- the complete `QuestionPackage` contract, which is deferred to V0.5;
- the full annotation-operation contract, which is deferred to a later specification.

## 2. Normative Language

The terms **MUST**, **MUST NOT**, **REQUIRED**, **SHOULD**, **SHOULD NOT**, and **MAY** are normative.

The **Session Core** is the backend authoritative command processor. **Publication** is the single atomic canonical mutation that makes a validated `TeachingScene` the current public scene. **Prepared package** is the verified immutable offline lesson bundle described in V0.1 and V0.2.

### 5.2 Field Definitions

#### `contractName`

- **Meaning:** Identifies the boundary contract as `TeachingScene`.
- **Required/optional:** Required.
- **Producer:** Every scene producer.
- **Consumer:** Renderer, cache, and projection compatibility layers.
- **Validation:** MUST equal the fixed value `TeachingScene`. Unknown names are `MALFORMED_SCENE`.
- **Security/privacy:** Prevents type confusion between unrelated contracts.
- **Lifecycle:** Immutable for the lifetime of the contract version.

#### `contractVersion`

- **Meaning:** The semantic version of the `TeachingScene` contract.
- **Required/optional:** Required.
- **Producer:** Every scene producer.
- **Consumer:** Renderer compatibility layer.
- **Validation:** MUST be a supported version. Version `0.1` is defined as supported.
- **Security/privacy:** Unsupported versions MUST fail closed before rendering.
- **Lifecycle:** Fixed per scene; governs interpretation, migration, and deprecation.

#### `sceneId`

- **Meaning:** A stable opaque identity for this scene across its lifecycle.
- **Required/optional:** Required.
- **Producer:** Scene producer or Session Core.
- **Consumer:** Renderer, cache, navigation, reveal, and annotation references.
- **Validation:** MUST be non-empty, bounded, and unique within the lesson/package. MUST NOT be parsed as a number or path.
- **Security/privacy:** Identity alone is not authority; references are resolved against canonical state.
- **Lifecycle:** Stable from creation through prepared caching and publication.

#### `sceneRevision`

- **Meaning:** The canonical revision of the scene produced at publication.
- **Required/optional:** Required.
- **Producer:** Session Core.
- **Consumer:** Renderer, cache, and projections.
- **Validation:** MUST be the session revision at which the scene became canonical, or a package-stable scene revision for prepared scenes.
- **Security/privacy:** Used for staleness checks and cache migration.
- **Lifecycle:** Immutable for a published scene; a replacement scene has a new identity or an explicitly versioned successor reference.

#### `sceneType`

- **Meaning:** The semantic scene type.
- **Required/optional:** Required.
- **Producer:** Scene producer.
- **Consumer:** Renderer and validation.
- **Validation:** MUST be one of the locked scene types in Section 6.
- **Security/privacy:** Unknown scene types MUST fail closed.
- **Lifecycle:** Fixed for the lifetime of the scene.

#### `rendererContractVersion`

- **Meaning:** The renderer capability contract version required to safely render this scene.
- **Required/optional:** Required.
- **Producer:** Scene producer or renderer-readiness boundary.
- **Consumer:** Classroom Display renderer.
- **Validation:** MUST reference a supported renderer capability version.
- **Security/privacy:** Prevents a scene from being interpreted by an incompatible renderer.
- **Lifecycle:** Fixed per scene; used in cache compatibility and invalidation.

#### `sessionId`

- **Meaning:** The authoritative classroom session that published this scene.
- **Required/optional:** Conditional; present for published live scenes. Absent for standalone prepared-scene artifacts before session binding.
- **Producer:** Session Core.
- **Consumer:** Projections, diagnostics, and cache binding.
- **Validation:** When present, MUST reference an existing session.
- **Security/privacy:** All public projection and reveal rules are scoped to this session.
- **Lifecycle:** Set at publication; immutable thereafter.

#### `lessonId`

- **Meaning:** The immutable lesson version the scene belongs to.
- **Required/optional:** Required.
- **Producer:** Lesson/preparation boundary.
- **Consumer:** Prepared cache, navigation, and curriculum validation.
- **Validation:** MUST reference a pinned lesson version.
- **Security/privacy:** Lesson binding prevents cross-lesson cache confusion.
- **Lifecycle:** Fixed at scene creation; repinning a lesson invalidates prior prepared scenes.

#### `lessonPosition`

- **Meaning:** The scene's ordered position within the prepared lesson.
- **Required/optional:** Required.
- **Producer:** Lesson/preparation boundary.
- **Consumer:** Navigation, prepared cache, and progressive disclosure.
- **Validation:** MUST be a stable ordinal within the lesson.
- **Security/privacy:** Position is not authority; navigation still resolves through canonical state.
- **Lifecycle:** Stable within an immutable lesson version.

#### `curriculumReference`

- **Meaning:** The pinned controlled curriculum source and version the scene aligns to.
- **Required/optional:** Conditional; REQUIRED when the scene asserts curriculum alignment. OPTIONAL when the lesson configured curriculum override as off.
- **Producer:** Curriculum grounding boundary.
- **Consumer:** Curriculum validation and diagnostics.
- **Validation:** MUST reference a controlled, versioned curriculum source. Model recollection is not authority.
- **Security/privacy:** Curriculum provenance is public metadata; internal mapping detail remains system-only.
- **Lifecycle:** Pinned at scene creation; changing curriculum version is outside an active classroom session.

#### `objects`

- **Meaning:** The ordered collection of renderer-safe semantic objects composing the scene.
- **Required/optional:** Required.
- **Producer:** Scene producer.
- **Consumer:** Renderer and object validation.
- **Validation:** MUST conform to the finite object model in Section 7. MUST NOT contain arbitrary HTML, CSS, scripts, executable code, arbitrary component names, or arbitrary renderer instructions.
- **Security/privacy:** Each object is independently validated; unsafe or unsupported objects fail the whole scene.
- **Lifecycle:** Object identities are stable; scene publication replaces the object set atomically.

#### `semanticLayout`

- **Meaning:** Technology-neutral semantic relationships among objects.
- **Required/optional:** Required.
- **Producer:** Scene producer.
- **Consumer:** Renderer layout engine.
- **Validation:** MUST use only the relationships in Section 8. MUST NOT contain pixel coordinates, CSS, font families, raw sizes, animations, breakpoints, or arbitrary absolute layout.
- **Security/privacy:** Semantic layout is data, not instructions.
- **Lifecycle:** Evaluated by the renderer; not independently mutable.

#### `revealGroups`

- **Meaning:** Deterministic groups that control progressive disclosure of existing stable content.
- **Required/optional:** Conditional; REQUIRED for scenes containing hints, answers, or solution steps.
- **Producer:** Scene producer.
- **Consumer:** Renderer and TeachingAction `PRESENTATION_CONTROL`.
- **Validation:** MUST reference existing stable object identities with valid ordering and absolute reveal state.
- **Security/privacy:** Answers and private-looking elements MUST remain unrevealed by default unless the reveal state is explicitly public.
- **Lifecycle:** Reveal state changes through canonical actions, not through scene regeneration.

#### `questionPackage`

- **Meaning:** A reference to, or bounded embedded representation of, a validated question package.
- **Required/optional:** Conditional; REQUIRED for `QUESTION` scenes and other scenes exposing question content.
- **Producer:** Scene producer.
- **Consumer:** Renderer, reveal, and QuestionPackage validation (V0.5).
- **Validation:** MUST be consistent with the public question content actually rendered. Answer/hint/solution consistency is validated before publication.
- **Security/privacy:** Answers and full solutions are not public by default; they are referenced by reveal groups, not embedded as visible text.
- **Lifecycle:** Detailed QuestionPackage semantics are deferred to V0.5.

#### `provenance`

- **Meaning:** Traceable origin information for the scene content.
- **Required/optional:** Required.
- **Producer:** Scene producer.
- **Consumer:** Diagnostics, curriculum validation, and audit.
- **Validation:** MUST record generation source, source classification, and applicable validator identities without embedding raw AI material.
- **Security/privacy:** Internal AI reasoning and intermediate candidates are system-only; public provenance is minimal.
- **Lifecycle:** Immutable for the lifetime of the scene.

#### `validationStatus`

- **Meaning:** The authoritative validation state of the scene.
- **Required/optional:** Required.
- **Producer:** Session Core validation boundary.
- **Consumer:** Publication gate, renderer readiness, and projections.
- **Validation:** MUST be one of the states in Section 11.
- **Security/privacy:** A scene with incomplete or failed validation MUST NOT be published.
- **Lifecycle:** Computed before publication; immutable after acceptance.

#### `validatorVersions`

- **Meaning:** The versions of deterministic and semantic validators applied to the scene.
- **Required/optional:** Conditional; REQUIRED when validators produced evidence.
- **Producer:** Validation boundary.
- **Consumer:** Diagnostics, reproducibility, and renderer readiness.
- **Validation:** MUST reference supported validator versions.
- **Security/privacy:** Validator evidence is traceable; internal diagnostics remain system-only.
- **Lifecycle:** Recorded with the scene.

#### `integrity`

- **Meaning:** A digest marker binding the scene's canonical content and contract version.
- **Required/optional:** Required.
- **Producer:** Scene producer or Session Core.
- **Consumer:** Renderer, prepared cache, and projections.
- **Validation:** MUST be recomputed and verified before render or cache acceptance.
- **Security/privacy:** Prevents tampered or corrupted prepared scenes from being rendered.
- **Lifecycle:** Fixed for the scene's exact content.

#### `language`

- **Meaning:** The primary natural language of learner-facing text.
- **Required/optional:** Required.
- **Producer:** Scene producer.
- **Consumer:** Renderer, accessibility, and localization.
- **Validation:** MUST be a supported language tag.
- **Security/privacy:** Language is public metadata.
- **Lifecycle:** Fixed per scene.

#### `presentation`

- **Meaning:** Bounded, technology-neutral presentation hints.
- **Required/optional:** Required.
- **Producer:** Scene producer.
- **Consumer:** Renderer.
- **Validation:** MUST contain only allowed hints such as content density class, primary focus, and readable hierarchy. MUST NOT contain styling, animation, or absolute coordinates.
- **Security/privacy:** Presentation hints are data, not instructions.
- **Lifecycle:** Interpreted by the renderer; not independently mutable.

#### `createdAt`

- **Meaning:** The scene's creation timestamp.
- **Required/optional:** Required.
- **Producer:** Scene producer.
- **Consumer:** Diagnostics and cache.
- **Validation:** MUST be a valid timestamp.
- **Security/privacy:** Public metadata only.
- **Lifecycle:** Fixed at creation.

#### `generatedBy`

- **Meaning:** Source classification of the scene: AI-generated, prepared-lesson, teacher-assembled, or system-assembled.
- **Required/optional:** Required.
- **Producer:** Scene producer.
- **Consumer:** Provenance, diagnostics, and policy.
- **Validation:** MUST be one of the defined source classifications.
- **Security/privacy:** Source classification is not authority; AI-generated scenes still require full validation.
- **Lifecycle:** Fixed at creation.

## 6. Scene Type Taxonomy

### 6.1 Locked Scene Types

The following scene types are derived from Product Discovery V0.3. No additional scene type is introduced.

| Scene type | Purpose | Expected object families | TeachingAction interactions | Generation allowed | Prepared-lesson eligible | Offline usable | Validation requirements | Accessibility considerations |
|---|---|---|---|---|---|---|---|---|
| `TITLE` | Introduce the lesson or a section | text | `NAVIGATE`, `PRESENTATION_CONTROL` | Yes | Yes | Yes | Text and layout safety | Large readable title, single focus |
| `CONCEPT` | Present a core concept | text, mathematics, geometric shape, fraction | `GENERATE`, `MODIFY`, `EXPLAIN`, `PRESENTATION_CONTROL` | Yes | Yes | Yes | Math and curriculum when applicable | Simple readable structure |
| `EXAMPLE` | Show a worked example | text, mathematics, equation, geometric shape | `GENERATE`, `MODIFY`, `EXPLAIN`, `PRESENTATION_CONTROL` | Yes | Yes | Yes | Math validation required | Progressive disclosure |
| `QUESTION` | Present a question to learners | text, mathematics, question-package reference | `GENERATE`, `MODIFY`, `PRESENTATION_CONTROL`, `ASSESS` | Yes | Yes | Yes | QuestionPackage consistency | Question readable without answer leakage |
| `EXPLANATION` | Explain reasoning or process | text, mathematics, equation, list, geometric shape | `GENERATE`, `MODIFY`, `PRESENTATION_CONTROL` | Yes | Yes | Yes | Math validation when applicable | Progressive disclosure |
| `DISCUSSION` | Frame classroom discussion | text, list | `GENERATE`, `MODIFY`, `PRESENTATION_CONTROL` | Yes | Yes | Yes | Text and layout safety | Low-density, non-competing text |
| `SUMMARY` | Summarize the lesson or section | text, list | `GENERATE`, `MODIFY`, `PRESENTATION_CONTROL` | Yes | Yes | Yes | Text and layout safety | Large readable summary |
| `FREE_CANVAS` | Open canvas for annotation and drawing | annotation anchor, geometric shape | `CANVAS_CONTROL`, `ASSESS`, `PRESENTATION_CONTROL` | Partially: structure only; teacher ink is separate | Yes | Yes | Annotation separation; no generated executable content | Touch/stylus fallback mode |

### 6.2 Scene Type Rules

- A scene MUST declare exactly one `sceneType`.
- `FREE_CANVAS` MUST preserve the generated/annotation layer separation.
- `QUESTION` scenes MUST reference or embed a validated question package and MUST NOT leak answers by default.
- A scene type not supported by the renderer MUST fail closed.

## 7. Object Model

### 7.1 Renderer-Safe Object Families

The object model is finite and renderer-safe. The following families are supported by Pendago MVP:

| Object family | Stable identity | Semantic role | Content payload | Allowed constraints | Visibility/reveal semantics | Interaction semantics | Validation expectations | Accessibility representation |
|---|---|---|---|---|---|---|---|---|
| `text` | Required | Narrative, label, or structural text | Plain semantic text | Length bounds, text role | Revealable via reveal group | Selectable, not editable | No executable markup | Accessible text label |
| `mathematics` | Required | Validated mathematical expression | Structured expression data | Representation kind | Revealable via reveal group | Selectable, not editable | Deterministic math validation | Alternative text for math |
| `equation` | Required | Equation or equivalence statement | Structured equation data | Step relation | Revealable via reveal group | Selectable | Deterministic math validation | Alternative text |
| `fraction` | Required | Fraction representation | Fraction semantic parts | Representation kind | Revealable via reveal group | Selectable | Deterministic math validation | Fraction read-aloud label |
| `geometric_shape` | Required | Geometric figure | Bounded shape kind | Allowed shapes only | Revealable via reveal group | Selectable, not editable | Shape constraints valid | Shape description text |
| `list` | Required | Ordered or unordered list | List of semantic items | Item count bounds | Revealable via reveal group | Selectable | No executable markup | List semantics |
| `image_reference` | Required | External visual reference | Controlled asset reference | Allowed source | Revealable via reveal group | Non-executable display | Asset integrity and availability | Alternative text required |
| `annotation_anchor` | Required | Anchor for annotation layer | Anchor identity | Scene/object binding | Not revealable as content | Ink layer attaches | Identity and lineage valid | No standalone visual content |

### 7.2 Roles Within Families

The following requested concepts are represented as constrained roles of existing families rather than separate families:

| Requested concept | Representation |
|---|---|
| Heading | `text` with semantic role `heading` |
| Mathematical expression | `mathematics` |
| Equation | `equation` |
| Question | `QUESTION` scene plus `questionPackage` reference; not a primitive object |
| Answer placeholder | Reveal group target, not a primitive object |
| Hint | Reveal group target, not a primitive object |
| Solution step | Reveal group target, not a primitive object |

### 7.3 Deferred or Unsupported Objects

The following are NOT part of the V0.4 MVP object set:

| Concept | Status |
|---|---|
| Number line | Deferred by Product Discovery V0.4 |
| Coordinate/graph representation | Post-MVP |
| Table | Not in locked product-discovery object families |
| Diagram | Not in locked product-discovery object families |
| Arbitrary image/media reference | Only controlled `image_reference` where supported |

These deferred or unsupported families are addressed in `Decisions Requiring Product Approval`.

### 7.4 Prohibited Content

No object MAY contain:

- arbitrary HTML;
- arbitrary CSS;
- scripts or executable code;
- arbitrary component names;
- arbitrary renderer instructions;
- absolute pixel coordinates except where mathematically meaningful in a geometric shape;
- raw AI reasoning or intermediate candidate fragments;
- credentials, pairing secrets, or raw audio.

### 7.5 Object Identity and Lifecycle

- Every renderable object has a stable opaque identity within its scene.
- Object identities MUST NOT be reused for different content within the same scene.
- A scene publication replaces the object set atomically; it does not mutate individual objects.
- Annotation objects are separate from generated objects and follow their own lifecycle.

## 8. Semantic Layout

### 8.1 Allowed Semantic Relationships

The scene producer MAY express the following relationships:

- sequence;
- grouping;
- emphasis;
- comparison;
- side-by-side relation;
- hierarchy;
- alignment intent;
- primary/secondary content.

### 8.2 Forbidden Presentation Instructions

The scene producer MUST NOT dictate:

- pixel coordinates unless mathematically meaningful in a geometric object;
- CSS;
- font families;
- raw font sizes;
- arbitrary absolute layout;
- animations;
- responsive breakpoints.

The renderer owns final visual layout, typography, spacing, and animation.

### 8.3 Layout Safety Rules

- Content MUST prefer large, readable typography and high contrast.
- One scene SHOULD focus on one primary concept or visual.
- The renderer MUST split overcrowded content into multiple scenes rather than shrink typography until content fits.
- The official minimum target is 1280×720; preferred is 1920×1080.
- 1024×768 MAY receive best-effort compatibility but is not the primary design target.
- Responsive adaptation is renderer behavior; it MUST NOT change semantic content or reveal state.
- Portrait/landscape differences are renderer adaptations and MUST NOT reorder semantic sequence or leak hidden content.

## 9. Reveal Model

### 9.1 `revealGroups`

A reveal group is a deterministic, ordered set of stable object or package-element references that controls progressive classroom disclosure.

Supported reveal content:

- hints;
- solution steps;
- answers;
- progressive explanations;
- prepared reveal sequences.

### 9.2 Rules

- Reveal state is deterministic and absolute: a referenced element is visible or hidden.
- Every reveal target has a stable identity.
- Reveal ordering MUST be explicit and monotonic within a prepared sequence.
- Show/hide transitions MUST NOT create or destroy objects; they only change public reveal state.
- Revealing prepared content normally MUST NOT require a new AI call.
- `PRESENTATION_CONTROL` actions reference reveal groups by stable identity.

### 9.3 Public/Private Implications

- Answers and full solution steps default to hidden.
- A private answer MUST NOT become public merely because it exists in the scene.
- Public reveal requires a separate canonical `PRESENTATION_CONTROL` action.

### 9.4 Offline Behavior

- Prepared reveal data is cached with the prepared scene.
- Offline-eligible reveal actions use absolute desired states and reconcile through the V0.2 provisional journal.

## 10. Generated Versus Annotation Layers

`TeachingScene` preserves the locked separation:

```text
TeachingScene
├── Generated Layer
└── Annotation Layer
```

### 10.1 Generated Layer

- **Ownership:** Scene producer and Session Core.
- **Identity:** Stable generated object identities.
- **Lifecycle:** Replaced only by a complete validated scene publication.
- **Mutation boundary:** Not directly mutated by teacher ink.
- **Clear behavior:** Clearing annotations does not affect this layer.
- **Replacement behavior:** A new scene publication replaces the generated layer atomically.
- **Revision semantics:** The generated layer is part of the published scene.

### 10.2 Annotation Layer

- **Ownership:** Teacher and student ink; display-local for offline provisional operations.
- **Identity:** Separate stable annotation identities.
- **Lifecycle:** Independent from generated scene lifecycle.
- **Mutation boundary:** Ink, erase, undo, redo, and confirmed clear operate only here.
- **Clear behavior:** Clearing ink MUST NEVER delete the generated scene.
- **Replacement behavior:** Scene replacement preserves applicable annotations subject to target-lineage validation.
- **Revision semantics:** Annotation changes are canonical mutations; offline changes are provisional until reconciliation.

The full annotation-operation contract is deferred to a later specification.

## 11. Atomic Publication and Validation Lifecycle

### 11.1 Publication Pipeline

Candidate `TeachingScene` MUST pass, in order:

```text
Candidate TeachingScene
        ↓
Schema validation
        ↓
Mathematics validation
        ↓
Curriculum validation
        ↓
Visibility/policy validation
        ↓
Renderer-readiness validation
        ↓
Approval where required
        ↓
Atomic publication
```

### 11.2 Validation States

| State | Meaning | Public effect |
|---|---|---|
| `CANDIDATE` | Scene is privately produced and not yet fully validated | None |
| `SCHEMA_VALIDATING` | Envelope and object model being checked | None |
| `MATH_VALIDATING` | Deterministic mathematics being checked | None |
| `CURRICULUM_VALIDATING` | Curriculum provenance being checked | None |
| `RENDERER_READY` | All readiness checks passed | None until publication |
| `APPROVAL_PENDING` | Validated scene awaits teacher approval | None |
| `REJECTED` | Validation or approval failed | None; last stable scene remains |
| `PUBLISHED` | Scene committed atomically as current public scene | Replaces last stable scene |

### 11.3 Candidate Behavior

- The current stable public scene MUST remain unchanged until publication succeeds.
- A candidate never enters the public projection.
- Malformed or invalid candidates are repaired or regenerated privately.
- Each repaired or regenerated candidate has a new integrity hash and invalidates prior approval.
- Failed, timed-out, stale, or post-termination candidates cannot mutate canonical state.

### 11.4 Regeneration and Timeout

- Regeneration changes the candidate identity/hash and requires revalidation.
- A timed-out candidate is cleared as a terminal workflow outcome; the last stable scene remains visible.

## 12. Renderer Readiness

A scene is renderer-ready only when ALL of the following hold:

- supported `contractName` and `contractVersion`;
- supported `rendererContractVersion`;
- supported `sceneType`;
- supported object types only;
- valid, unique, stable object identities;
- complete required fields;
- valid reveal references;
- valid asset references with available or integrity-verified assets;
- valid semantic layout relationships;
- valid mathematical data with required validation evidence;
- valid curriculum references where required;
- accessibility minimums present;
- integrity verification passes.

The renderer MUST reject unsupported or unsafe scene data before rendering. The display MUST validate a scene away from the visible renderer and atomically replace the current projection.

## 13. QuestionPackage Integration

The complete `QuestionPackage` contract is deferred to V0.5. This specification defines only the scene boundary:

- A `QUESTION` scene references or contains a bounded, validated `questionPackage` representation.
- Only the question's public portion is projected to the display by default.
- Answers, hints, and solution steps are referenced through reveal groups, not embedded as public visible content.
- Offline/prepared scenes MUST include all reveal data and question-package elements required for cached progressive disclosure.
- The question, correct answer, solution steps, hints, and explanation MUST be consistent before publication.

## 14. Curriculum and Provenance

A scene records:

- curriculum source and version;
- topic/concept mapping;
- alignment override where the lesson explicitly disabled curriculum alignment;
- content provenance;
- generation source classification;
- validator identity and version.

Rules:

- The LLM is never curriculum authority.
- Curriculum-sensitive scenes use the pinned controlled curriculum version.
- Curriculum override is a teacher lesson configuration; it does not remove deterministic math validation.
- Internal AI reasoning and intermediate candidates are system-only.

## 15. Mathematics Boundary

`TeachingScene` obligations for deterministic mathematics:

- Mathematical expressions, equations, fractions, answers, transformations, and worked examples MUST use structured validated representations.
- Canonical values MUST be recorded where a deterministic answer exists.
- Representation consistency MUST be validated between semantic parts and visible text.
- Validator evidence reference MUST be traceable to the published scene.
- Unsupported or inconclusive mathematics MUST be recorded as not validated and MUST gate public publication.
- The LLM may propose mathematics but never certifies correctness.

## 16. Prepared Lesson Cache

A prepared/offline lesson scene MUST include:

- immutable/versioned scene identity and scene revision;
- complete asset data or integrity-verified references;
- complete reveal data;
- complete question-package reveal data where applicable;
- integrity metadata;
- pinned curriculum version;
- supported renderer contract compatibility.

Rules:

- The display MUST NOT report classroom-ready when required scene resources are missing.
- Cached scenes are integrity-checked before rendering.
- A package or curriculum repin invalidates prior prepared scenes and display verification.
- Unsupported renderer versions invalidate the prepared cache for that display.

## 17. Visibility and Projections

### 17.1 Public Scene Data

The public `TeachingScene` MAY contain only learner-authorized content:

- visible scene content;
- public lesson position;
- public reveal state;
- public annotation layer;
- public validation/provenance markers when product design requires them.

### 17.2 Private and System Data

The public scene MUST NOT embed:

- private answers;
- internal validation diagnostics;
- AI reasoning or intermediate candidates;
- security metadata, credentials, or pairing secrets;
- raw audio.

The display receives an independently built public projection. It MUST NOT rely on client-side hiding of private fields.

## 18. Contract Evolution

### 18.1 Versioning

- `TeachingScene` versions are semantic and monotonic.
- The contract version is carried in every scene.
- Unknown versions fail closed.

### 18.2 Renderer Compatibility

- A renderer advertises its supported `rendererContractVersion`.
- A scene requiring an unsupported renderer version is rejected before rendering.

### 18.3 Additive Versus Breaking Changes

- Additive optional object families or metadata MAY be introduced in a backward-compatible minor version.
- Breaking changes include removing or renaming a required field, changing field types, repurposing a scene type, or changing visibility semantics.

### 18.4 Scene Type and Object Type Evolution

- New scene types require product-discovery support and an ADR or superseding specification.
- New object families require renderer capability, validation support, and an explicit architecture decision.
- Repurposing an existing scene or object type is breaking.

### 18.5 Deprecation

- A field or object family MAY be deprecated in a minor version while remaining accepted for backward compatibility.
- Deprecated elements MUST document a removal version.

### 18.6 Mixed Client Versions and Prepared Cache

- A display using an unsupported version becomes read-only on its last safe scene and requests compatible recovery.
- Prepared-cache migration or invalidation occurs when scene contract, renderer contract, package, or curriculum versions change.
- A stale scene revision is never rendered over a newer canonical scene.

## 19. Failure Model

| Failure category | Publication behavior | Teacher-facing behavior | Client recovery instruction | System diagnostic boundary |
|---|---|---|---|---|
| `MALFORMED_SCENE` | Block publication | Private "konten tidak valid" notice | Recreate or repair candidate | Full validation path internally |
| `UNSUPPORTED_CONTRACT_VERSION` | Block publication | Compatibility notice | Request compatible contract or read-only recovery | Contract and supported range |
| `UNSUPPORTED_RENDERER_VERSION` | Block publication | Renderer compatibility notice | Update or use compatible display | Scene and renderer versions |
| `UNSUPPORTED_SCENE_TYPE` | Block publication | Unsupported-scene notice | Use supported scene type | Scene type and supported set |
| `UNSUPPORTED_OBJECT` | Block publication | Unsupported-content notice | Remove or replace object | Object family and supported set |
| `INVALID_REFERENCE` | Block publication | Reference-error notice | Reselect target | Reference and resolution state |
| `INVALID_REVEAL_GROUP` | Block publication | Reveal-error notice | Rebuild reveal group | Reveal target and ordering |
| `INVALID_MATH` | Block publication | Private math-validation notice | Correct or regenerate math | Validation evidence class only |
| `CURRICULUM_VALIDATION_FAILURE` | Block publication | Private curriculum notice | Realign or explicitly override | Curriculum provenance class |
| `UNSAFE_VISIBILITY` | Block publication | Private visibility notice | Change visibility request | Visibility policy result |
| `MISSING_ASSET` | Block publication or exclude scene | Missing-asset notice | Provide or restore asset | Asset reference and cache status |
| `RENDERER_READINESS_FAILURE` | Block publication | Readiness notice | Resolve renderer prerequisite | Missing readiness criterion |
| `INTEGRITY_FAILURE` | Block publication/cache acceptance | Corruption notice | Re-download or revalidate package | Integrity digest status |
| `STALE_SCENE_REVISION` | Block publication | "Konteks berubah" notice | Resync to current snapshot | Expected and current revision |

Error responses MUST reveal only role-appropriate information. The display MUST NOT receive private validation detail, internal AI reasoning, credentials, or raw audio.

## 20. Examples and Counterexamples

### 20.1 Simple Explanation Scene

An `EXPLANATION` scene contains a heading-as-text object, short readable text objects, and a validated `mathematics` object. Semantic layout expresses sequence and primary emphasis. No layout coordinates or styles are present.

### 20.2 Fraction Scene

A `CONCEPT` or `EXAMPLE` scene contains a `fraction` object with semantic numerator/denominator parts and a validated equivalence claim. The renderer chooses the visual fraction representation from supported renderer capabilities.

### 20.3 Equation-Solving Scene

An `EXAMPLE` scene contains `equation` objects with step relations. Each step is a separate stable object in sequence. Answers and later steps are hidden in reveal groups.

### 20.4 Progressive Hint Scene

A `QUESTION` scene references a question package and reveal groups for hint 1, hint 2, step 1, step 2, and the answer. All are hidden by default; `PRESENTATION_CONTROL` reveals them in order.

### 20.5 Prepared Offline Scene

A prepared `EXPLANATION` scene contains all visible text, math, reveal data, and integrity metadata. The display verifies integrity and renderer compatibility before marking the package classroom-ready.

### 20.6 AI-Generated Candidate Awaiting Validation

An AI boundary produces a `CANDIDATE` scene with `validationStatus: SCHEMA_VALIDATING`. The current public scene remains unchanged. The candidate never reaches the display until it becomes `RENDERER_READY` and is published.

### 20.7 Valid Scene With Annotations

A published `CONCEPT` scene has a generated layer and a separate annotation layer containing teacher ink. Clearing ink leaves the generated layer unchanged.

### 20.8 Rejected Arbitrary HTML

A candidate containing `<div>`, `<script>`, or raw markup is rejected as `MALFORMED_SCENE` or `UNSUPPORTED_OBJECT`. It is never rendered.

### 20.9 Rejected Unsupported Object

A candidate containing a `diagram` object family is rejected as `UNSUPPORTED_OBJECT` because `diagram` is not in the MVP object set.

### 20.10 Rejected Private-Answer Leakage

A `QUESTION` scene attempts to embed the correct answer as visible public text. It is rejected as `UNSAFE_VISIBILITY`; the answer may only exist behind a hidden reveal group.

### 20.11 Rejected Invalid Mathematics

A candidate containing an invalid equation or inconsistent fraction fails deterministic math validation and is blocked from publication. The prior stable scene remains visible.

## 21. Invariants

1. `TeachingScene` is structured data, never renderer code.
2. Arbitrary HTML, CSS, scripts, executable code, arbitrary component names, and arbitrary renderer instructions cannot enter the renderer.
3. Every renderable object has a stable identity.
4. Public scenes contain only authorized public data.
5. Invalid mathematics cannot be publicly published.
6. Curriculum claims reference controlled curriculum data.
7. The current stable scene survives generation failure.
8. Scene publication is atomic.
9. Prepared cached scenes are integrity-checked.
10. Reveal transitions reference existing stable content.
11. Annotation lifecycle is separate from generated scene lifecycle.
12. Unsupported contracts, scene types, object families, and renderer versions fail closed.

## 22. Testable Acceptance Criteria

### 22.1 Schema Conformance

1. A scene missing a required field is rejected as `MALFORMED_SCENE`.
2. An unknown `contractName` or unsupported `contractVersion` is rejected before rendering.
3. Unknown fields are rejected or ignored only under a defined additive-version rule.

### 22.2 Renderer Compatibility

4. A scene requiring an unsupported `rendererContractVersion` is rejected.
5. A supported scene passes all renderer-readiness checks before publication.

### 22.3 Unsupported Objects

6. A scene containing an unsupported object family is rejected as `UNSUPPORTED_OBJECT`.
7. A scene containing arbitrary HTML, script, CSS, or executable instructions is rejected.

### 22.4 Layout Safety

8. A scene with pixel coordinates, font families, raw sizes, animations, or breakpoints is rejected.
9. Overcrowded content triggers scene splitting rather than shrinking typography below readability.

### 22.5 Reveal Behavior

10. Reveal groups reference existing stable object identities.
11. Prepared reveal transitions require no new AI call.
12. A reveal transition to an already-visible state is a defined no-op.

### 22.6 Public/Private Isolation

13. A public scene does not contain private answers, AI reasoning, credentials, or raw audio.
14. Negative projection tests prove private fields never reach the display.

### 22.7 Math Validation

15. A scene with invalid or unvalidated deterministic math is not published.
16. Published math has traceable validator evidence.

### 22.8 Curriculum Grounding

17. Curriculum-sensitive scenes reference the pinned controlled curriculum version.
18. A scene lacking required curriculum provenance is not published.

### 22.9 Atomic Publication

19. The current stable scene remains visible through generation, validation, approval, failure, or timeout.
20. A new scene becomes public only in one complete atomic commit.

### 22.10 Prepared Cache

21. A prepared scene with missing assets or failed integrity is not classroom-ready.
22. A package/curriculum/contract repin invalidates affected cached scenes.

### 22.11 Degraded Connectivity

23. Offline reveal and navigation operate on verified cached scenes only.
24. Online-only semantic scene changes are unavailable while degraded.

### 22.12 Contract Evolution

25. Unsupported scene or object versions fail closed.
26. Mixed-version displays become read-only and request compatible recovery.

### 22.13 Renderer Failure Recovery

27. A renderer that cannot validate a new scene retains the last safe scene.
28. A display with unsupported capability does not partially render an incompatible scene.

## 23. Decisions Requiring Product Approval

The following decisions are not resolved by locked inputs. Each item includes question, options, recommendation, rationale, and whether it blocks V0.4 lock.

### 23.1 Number Line Representation

**Question**
Should the `number_line` object family be included in MVP, or deferred as Product Discovery V0.4 states?

**Available options**

1. Defer number lines until after the fraction prototype.
2. Include number lines now as an MVP fraction representation.
3. Include only a constrained static number-line representation.

**Architecture impact**

- Adds an object family, validation requirements, and renderer capability.
- Affects prepared-cache and renderer-readiness scope.

**Recommended option**
Defer number lines until after the fraction prototype, consistent with Product Discovery V0.4.

**Rationale**
Product Discovery explicitly lists number lines as a later representation. Adding them now would expand MVP object scope without product approval.

**Blocks V0.4 lock:** No. The deferred status is explicit and the object set is complete without it.

### 23.2 Table and Diagram Object Families

**Question**
Should `table` and `diagram` be introduced as structured MVP object families?

**Available options**

1. Defer both until a demonstrated product need exists.
2. Introduce `table` only for comparison content.
3. Introduce `diagram` only for geometry/visual explanation.
4. Introduce both.

**Architecture impact**

- Expands the finite object model and renderer/validation responsibilities.
- Risks duplicating what geometric shapes and lists already provide.

**Recommended option**
Defer both until a concrete curriculum or pedagogy need is approved.

**Rationale**
The locked product-discovery object families do not include table or diagram. Adding them silently would violate the instruction not to expand unsupported assumptions.

**Blocks V0.4 lock:** No. The current object model is complete for MVP.

### 23.3 QuestionPackage Public Projection

**Question**
Which portions of a `QuestionPackage` may be embedded in a public `TeachingScene` versus referenced only?

**Available options**

1. Public question text embedded; answers/hints/solutions referenced through reveal groups.
2. Full package embedded with renderer-side hiding.
3. Full package referenced; scene contains only a package identity.

**Architecture impact**

- Determines public projection size and leakage risk.
- Affects offline completeness and V0.5 contract boundaries.

**Recommended option**
Embed the public question text; reference answers, hints, and solution steps through reveal groups. Defer full embedding semantics to V0.5.

**Rationale**
It avoids private-data leakage, keeps the public payload minimal, and leaves V0.5 to define the complete package contract.

**Blocks V0.4 lock:** No. The boundary rule is defined; detailed package semantics remain V0.5.

### 23.4 Accessibility Baseline

**Question**
What accessibility minimum is mandatory for MVP scene objects?

**Available options**

1. Text alternatives for non-text objects only.
2. Text alternatives plus contrast and font-size floors.
3. Full accessibility conformance beyond MVP.

**Architecture impact**

- Defines `accessibility` metadata and renderer obligations.
- Affects renderer-readiness checks.

**Recommended option**
Require text alternatives for non-text objects and enforce readable contrast/size as renderer policy; defer full conformance beyond MVP.

**Rationale**
It provides a safe readable baseline without over-committing to a certification level the product has not selected.

**Blocks V0.4 lock:** No. The minimum is defined; the conformance level is deferred.

### 23.5 Image/Media Asset Policy

**Question**
Which image or media reference types are supported in MVP, and what are their integrity and cache requirements?

**Available options**

1. Controlled static image references only, with alternative text and integrity.
2. Broader media including video and interactive assets.
3. No external media in MVP.

**Architecture impact**

- Defines `image_reference` validation and prepared-cache completeness.
- Affects offline behavior and asset availability checks.

**Recommended option**
Support controlled static image references only, with alternative text, integrity verification, and missing-asset failure behavior.

**Rationale**
It matches "image/reference visual when required" from Product Discovery V0.3 while avoiding unvalidated interactive or media complexity.

**Blocks V0.4 lock:** No. The constrained family is defined.
