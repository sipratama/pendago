# Pendago Architecture Specification V0.3

## TeachingAction Contract

**STATUS: PROPOSED — REQUIRES ARCHITECTURE APPROVAL**
**Date: September 4, 2026**
**Supersedes:** None
**Depends on:**

- [Pendago System Architecture V0.1](v0.1-system-architecture.md)
- [Pendago Architecture Specification V0.2](v0.2-session-lifecycle.md)

## 1. Purpose

This specification defines the canonical, versioned `TeachingAction` contract that all teacher-originated and system-mediated classroom actions use as their common command language.

`TeachingAction` is the normalized boundary object exchanged between:

- Teacher Smartphone Controller;
- manual classroom controls;
- voice interpretation;
- touch and stylus interaction;
- explicit ink-assessment requests;
- prepared-lesson navigation and reveal actions;
- system recovery and authority actions;
- the backend authoritative Session Core.

An AI component MAY propose a `TeachingAction` candidate, but it MUST NOT mutate canonical classroom state directly. Only the backend authoritative Session Core accepts and commits a `TeachingAction` as a canonical mutation.

This document does not define:

- frontend, backend, persistence, realtime, task-processing, AI-provider, container, cloud, or deployment technologies;
- framework manifests or production code;
- transport-specific JSON or WebSocket message schemas;
- the `TeachingScene` or `QuestionPackage` content contracts;
- exact confidence thresholds, timeout durations, or retention durations;
- user-interface design.

## 2. Normative Language

The terms **MUST**, **MUST NOT**, **REQUIRED**, **SHOULD**, **SHOULD NOT**, and **MAY** are normative.

The **Session Core** is the backend authoritative command processor. A **canonical mutation** is a successful command that changes canonical session state. A **projection** is a role-specific view independently derived from canonical state.

## 3. Authoritative Inputs and Constraints

This specification is constrained by:

1. all locked documents under `docs/product-discovery/`;
2. Pendago System Architecture V0.1;
3. Pendago Architecture Specification V0.2;
4. the ten Conditions of Approval in V0.1;
5. the session-lifecycle, revision, idempotency, display-epoch, visibility, and AI-publication invariants in V0.2.

`TeachingAction` is the versioned structured representation of teacher intent described in V0.1 Section 11 and V0.2 Section 14. It MUST NOT carry arbitrary executable markup or client-provided canonical state.

### 5.2 Field Definitions

#### `contractName`

- **Meaning:** Identifies the boundary contract as `TeachingAction`.
- **Required/optional:** Required.
- **Producer:** Every action producer.
- **Consumer:** Session Core.
- **Validation:** MUST equal the fixed value `TeachingAction`. Unknown names are `MALFORMED_ACTION`.
- **Security:** Prevents type confusion between unrelated contracts.
- **Lifecycle:** Immutable for the lifetime of the contract version.

#### `contractVersion`

- **Meaning:** The semantic version of the `TeachingAction` contract.
- **Required/optional:** Required.
- **Producer:** Every action producer.
- **Consumer:** Session Core compatibility layer.
- **Validation:** MUST be a supported version. The V0.3 specification defines version `0.1` as supported.
- **Security:** Unsupported versions MUST be rejected before any business processing to prevent schema confusion and injection of unknown fields.
- **Lifecycle:** Fixed per action; governs interpretation, migration, and deprecation.

#### `actionId`

- **Meaning:** A unique identity for this action instance, independent of its effect.
- **Required/optional:** Required.
- **Producer:** The origin client or system boundary.
- **Consumer:** Session Core, ordered command journal, projections, diagnostics, and client acknowledgments.
- **Validation:** MUST be non-empty, bounded in size, and unique at least within the session for a given producer. MUST NOT be parsed as a number or path.
- **Security:** Used for lineage and diagnostics; it MUST NOT be trusted as the idempotency or authorization key.
- **Lifecycle:** Stable for the lifetime of the action; one `actionId` is never reassigned to a different effect.

#### `idempotencyKey`

- **Meaning:** The stable identity used to detect duplicate or replaying mutation attempts.
- **Required/optional:** Required for mutation actions; not required for reads, heartbeats, or progress notifications.
- **Producer:** The origin client.
- **Consumer:** Session Core idempotency store.
- **Validation:** MUST be non-empty, bounded in size, and treated as opaque.
- **Security:** The idempotency binding is computed over session, actor, role, authority lineage, command type, normalized payload, contract version, applicable display identity and epoch, and security-relevant confirmation context. Reuse with a different binding is `IDEMPOTENCY_CONFLICT` and MUST be security-auditable.
- **Lifecycle:** Persisted with the original authoritative outcome; exact reuse returns that outcome without re-execution; conflicting reuse is terminal.

#### `correlationId`

- **Meaning:** Groups related actions and asynchronous results, such as an AI generation workflow and its later publication or rejection.
- **Required/optional:** Optional.
- **Producer:** Origin client, AI boundary, or Session Core.
- **Consumer:** Async workflow, projections, and diagnostics.
- **Validation:** If present, MUST be a bounded opaque identifier.
- **Security:** MUST NOT contain credentials or raw AI material; correlation is operational, not an authorization grant.
- **Lifecycle:** Stable across the correlated group; retained according to operational diagnostics policy.

#### `causationId`

- **Meaning:** Identifies the preceding action that caused or authorized this follow-up action.
- **Required/optional:** Conditional; REQUIRED for approval/rejection/cancel actions derived from an originating generation action, and for system actions that supersede a prior action.
- **Producer:** Controller for teacher decisions, or Session Core for system-derived actions.
- **Consumer:** Lineage validation, journal, and diagnostics.
- **Validation:** When present, MUST reference a prior action or workflow in the same session.
- **Security:** Follow-up actions MUST revalidate their own authority; causation alone does not inherit authorization.
- **Lifecycle:** Immutable causal reference.

#### `sessionId`

- **Meaning:** The authoritative classroom session this action targets.
- **Required/optional:** Required.
- **Producer:** Producing client.
- **Consumer:** Session Core session binding.
- **Validation:** MUST reference an existing session in a state that permits the intent.
- **Security:** All authorization, revision, epoch, and target checks are scoped to this session. Cross-session references are rejected.
- **Lifecycle:** Stable for the lifetime of the session; remains valid for post-termination reads only under retention policy.

#### `actorId`

- **Meaning:** The authenticated actor that originated the action.
- **Required/optional:** Required.
- **Producer:** Producing client from authenticated identity.
- **Consumer:** Session Core authorization.
- **Validation:** MUST be a stable opaque identifier bound to an authenticated principal.
- **Security:** MUST NOT be inferred from untrusted payload. Identity comes from the authentication boundary, not the action body.
- **Lifecycle:** Recorded with the action and any idempotency outcome.

#### `actorRole`

- **Meaning:** The role under which the actor attempts to act.
- **Required/optional:** Required.
- **Producer:** Producing client.
- **Consumer:** Session Core role authorization.
- **Validation:** MUST be one of the defined roles: `TEACHER`, `DISPLAY`, or `SYSTEM`. Future roles require contract evolution.
- **Security:** Role is a claim; authorization is enforced by the Session Core, not by the client.
- **Lifecycle:** Fixed per action; role restrictions are evaluated at acceptance time.

#### `deviceId`

- **Meaning:** The device identity associated with the action.
- **Required/optional:** Conditional; REQUIRED for display-originated actions and display-authority-sensitive actions. Optional for controller actions that do not depend on a specific device.
- **Producer:** Producing client.
- **Consumer:** Session Core device and epoch fencing.
- **Validation:** MUST be a stable opaque device identity when present.
- **Security:** A device identity alone is not authority; it is evaluated with the applicable role and epoch.
- **Lifecycle:** Recorded with display-authority actions.

#### `displayEpoch`

- **Meaning:** The monotonic display authority token under which the action claims authority.
- **Required/optional:** Conditional; REQUIRED for display-originated mutations and provisional operations. MUST be absent for controller-only actions that do not rely on display authority.
- **Producer:** Producing client.
- **Consumer:** Session Core display-epoch fencing.
- **Validation:** When required, MUST equal the current canonical display epoch. An old epoch is `STALE_DISPLAY_EPOCH`.
- **Security:** Old-epoch actions MUST NOT mutate canonical state and MUST NOT be silently rebased.
- **Lifecycle:** Monotonic; same-display reconnect does not increment it; replacement or revocation does.

#### `sourceModality`

- **Meaning:** The input modality from which the action originated.
- **Required/optional:** Required.
- **Producer:** Producing client or AI interpretation boundary.
- **Consumer:** Session Core, validation policy, and diagnostics.
- **Validation:** MUST be one of the modalities defined in Section 7.
- **Security:** Modality is metadata, not authorization; voice-derived actions remain untrusted regardless of modality.
- **Lifecycle:** Recorded with the action; does not change after creation.

#### `intent`

- **Meaning:** The structured action category requested.
- **Required/optional:** Required.
- **Producer:** Controller, display, AI interpretation boundary, or system recovery.
- **Consumer:** Session Core intent policy and command handler selection.
- **Validation:** MUST be one of the locked intents in Section 6. Unknown intents are `UNSUPPORTED_VERSION` or `MALFORMED_ACTION` per contract-evolution rules.
- **Security:** Intent-level authorization is enforced by the Session Core. A client cannot request an intent outside its role or current session state.
- **Lifecycle:** Fixed per action; drives execution classification and lifecycle eligibility.

#### `target`

- **Meaning:** The raw reference or selection the action is intended to operate on.
- **Required/optional:** Conditional; REQUIRED when the intent needs a target. Optional for session-wide or ambient actions.
- **Producer:** Controller, display, AI interpretation boundary, or system recovery.
- **Consumer:** Session Core reference resolver.
- **Validation:** MUST conform to the target model in Section 8. MUST NOT contain arbitrary object paths or executable references.
- **Security:** Target references are untrusted until resolved by the backend against canonical state.
- **Lifecycle:** The raw target is preserved; the authoritative resolved target is recorded in `resolvedTarget`.

#### `resolvedTarget`

- **Meaning:** The single authoritative target resolved by the Session Core.
- **Required/optional:** Backend-only; MUST NOT be accepted from a client.
- **Producer:** Session Core reference resolver.
- **Consumer:** Command handler, projections, journal, and diagnostics.
- **Validation:** MUST reference an existing canonical object or scene with a valid lineage when the intent requires it.
- **Security:** Clients cannot override resolution. This prevents LLM or client target confusion.
- **Lifecycle:** Computed at acceptance time and committed with the canonical mutation.

#### `constraints`

- **Meaning:** Structured intent-specific parameters such as difficulty, topic inheritance, representation, or scope.
- **Required/optional:** Optional.
- **Producer:** Controller, AI interpretation boundary, or deterministic control.
- **Consumer:** Session Core constraint validation and downstream generators/validators.
- **Validation:** MUST conform to the intent-specific constraint schema; unknown fields are rejected or ignored only under a defined additive-version rule.
- **Security:** Constraints are data, never executable instructions. They cannot override visibility, authorization, or validation policy.
- **Lifecycle:** Normalized into the idempotency binding; preserved with the action.

#### `visibility`

- **Meaning:** The requested visibility classification for the action result.
- **Required/optional:** Required.
- **Producer:** Controller, AI interpretation boundary, or deterministic control.
- **Consumer:** Session Core visibility policy and projection builder.
- **Validation:** MUST be `PUBLIC`, `PRIVATE_TEACHER`, or `SYSTEM`.
- **Security:** Requested visibility is a hint. Authorized visibility is computed by the Session Core. A client-requested `PUBLIC` cannot bypass private-by-default policy for answers or assessment results.
- **Lifecycle:** Requested visibility is preserved; resulting projection visibility is recorded separately.

#### `executionMode`

- **Meaning:** The teacher-selected execution posture: `AUTO` or `APPROVAL`.
- **Required/optional:** Required for controller-originated teaching actions. System-derived actions use a system policy rather than a teacher mode.
- **Producer:** Controller or AI interpretation boundary.
- **Consumer:** Session Core approval and publication boundary.
- **Validation:** MUST be `AUTO` or `APPROVAL` when present.
- **Security:** `AUTO` never bypasses deterministic validation, curriculum grounding, visibility policy, or destructive confirmation. It only relaxes the human approval gate for safe, high-confidence, non-destructive actions.
- **Lifecycle:** Evaluated at acceptance and again at publication for asynchronous results.

#### `confidence`

- **Meaning:** A structured, advisory measure of interpretation certainty from the AI boundary.
- **Required/optional:** Optional.
- **Producer:** AI interpretation boundary.
- **Consumer:** Session Core ambiguity policy and private teacher UI.
- **Validation:** When present, MUST be a bounded value, such as a normalized `0..1` score plus an optional qualitative band (`LOW`, `MEDIUM`, `HIGH`). No numeric threshold is locked by this specification.
- **Security:** Confidence is advisory evidence and MUST NOT substitute for deterministic validation or authorization. It MAY be shown privately to the teacher.
- **Lifecycle:** Operational by default; not canonical unless a later approved policy requires retention.

#### `ambiguity`

- **Meaning:** A structured statement of unresolved reference or intent ambiguity.
- **Required/optional:** Conditional; REQUIRED when the AI boundary cannot resolve a materially ambiguous reference.
- **Producer:** AI interpretation boundary.
- **Consumer:** Session Core clarification flow and private teacher UI.
- **Validation:** MUST identify the ambiguous slot and candidate alternatives without carrying raw prompt or audio data.
- **Security:** Ambiguity triggers a private clarification request, never a silent guess. It MUST NOT carry student or raw-audio material.
- **Lifecycle:** Operational clarification state; resolved by a follow-up action with the appropriate `causationId`.

#### `expectedSessionRevision`

- **Meaning:** The canonical session revision against which the action was composed.
- **Required/optional:** REQUIRED for normal online mutations. NOT required for reads or snapshot requests.
- **Producer:** Producing client from its last known projection revision.
- **Consumer:** Session Core optimistic-concurrency check.
- **Validation:** MUST equal the current canonical revision. A mismatch is `STALE_REVISION`.
- **Security:** Prevents silent rebasing of commands computed from stale context.
- **Lifecycle:** Evaluated at acceptance; not part of a defined no-op or read.

#### `createdAt`

- **Meaning:** The producer's creation timestamp.
- **Required/optional:** Required.
- **Producer:** Producing client.
- **Consumer:** Session Core expiry and replay checks.
- **Validation:** MUST be a valid timestamp. It is diagnostic metadata and is NOT trusted as authoritative time unless the backend policy requires it.
- **Security:** Used for bounded replay protection; clock skew MUST NOT grant authority or bypass expiry.
- **Lifecycle:** Recorded with the action.

#### `expiresAt`

- **Meaning:** The action's requested expiry timestamp.
- **Required/optional:** Required for mutations.
- **Producer:** Producing client.
- **Consumer:** Session Core expiry enforcement.
- **Validation:** MUST be a valid timestamp no later than the session boundary or an intent-specific policy cap. The backend MAY shorten a requested expiry.
- **Security:** Expired actions are rejected without canonical mutation. Replay attempts after expiry are terminal for that action identity.
- **Lifecycle:** Expiry is evaluated before idempotency and revision checks.

#### `authorityLineage`

- **Meaning:** The authority lineage proving the actor/device currently holds the claimed authority.
- **Required/optional:** Required for mutations requiring controller or display authority.
- **Producer:** Producing client.
- **Consumer:** Session Core authority fencing.
- **Validation:** MUST match the current canonical authority lineage for the role and device.
- **Security:** Stale lineage is rejected before mutation. Takeover or replacement revokes prior lineage.
- **Lifecycle:** Changes only through canonical authority grant, takeover, activation, replacement, or revocation.

#### `confirmation`

- **Meaning:** Explicit evidence of a required destructive-action confirmation.
- **Required/optional:** Conditional; REQUIRED for destructive actions such as clear-ink, termination, or display replacement.
- **Producer:** Producing client.
- **Consumer:** Session Core confirmation policy.
- **Validation:** MUST bind to the action and the confirmed consequence without storing secrets.
- **Security:** Confirmation prevents accidental destructive mutation and is included in the idempotency binding.
- **Lifecycle:** Recorded with the accepted action.

#### `preconditions`

- **Meaning:** Structured target-lineage or dependency preconditions that must still hold at acceptance time.
- **Required/optional:** Optional; RECOMMENDED for asynchronous actions targeting a specific scene or object lineage.
- **Producer:** Producing client or AI boundary.
- **Consumer:** Session Core precondition validator.
- **Validation:** MUST reference canonical identity and lineage; failure is `STALE_TARGET` or `PRECONDITION_FAILED`.
- **Security:** Preconditions prevent stale AI publication against a changed scene.
- **Lifecycle:** Evaluated at acceptance and, for asynchronous work, re-evaluated at publication.

### 6.2 Intent Details

#### `GENERATE`

- **Purpose:** Create a new structured `TeachingScene`, `QuestionPackage`, or scene object from a teacher request.
- **Allowed actors:** `TEACHER`.
- **Allowed source modalities:** `VOICE`, `MANUAL`, `TOUCH`; `PREPARED_LESSON` only in preparation context.
- **Expected target types:** Current scene, active object, explicit reference, or ambient/no target.
- **AI interpretation allowed:** Yes. Natural-language constraints are interpreted into structured generation requests.
- **Deterministic execution possible:** No. The LLM proposes; deterministic engines validate.
- **Teacher approval may be required:** Yes. Generative results follow Auto/Approval rules in Section 9.
- **Public mutation possible:** Only through one complete atomic publication commit; the action itself enters an async workflow without changing the public scene.
- **Expected failure modes:** `GENERATION_UNAVAILABLE`, `VALIDATION_FAILURE`, `BUSY_WORKFLOW`, `AMBIGUOUS_REFERENCE`, `STALE_REVISION`, `STALE_DISPLAY_EPOCH`, `TIMEOUT`.

#### `MODIFY`

- **Purpose:** Change existing structured content while preserving its identity and lineage.
- **Allowed actors:** `TEACHER`.
- **Allowed source modalities:** `VOICE`, `MANUAL`, `TOUCH`, `STYLUS`.
- **Expected target types:** Explicit object, active object, or current scene.
- **AI interpretation allowed:** Yes for natural-language semantic changes.
- **Deterministic execution possible:** Partially. Deterministic for explicit structured property edits; not deterministic for semantic rewording or conceptual changes.
- **Teacher approval may be required:** Yes when the modification is generative or materially changes public learner-facing content.
- **Public mutation possible:** Yes, only after validation and, when required, approval.
- **Expected failure modes:** `UNRESOLVED_REFERENCE`, `AMBIGUOUS_REFERENCE`, `STALE_TARGET`, `VALIDATION_FAILURE`, `FORBIDDEN_INTENT`, `STALE_REVISION`.

#### `EXPLAIN`

- **Purpose:** Produce or reveal explanation, rationale, or solution progression.
- **Allowed actors:** `TEACHER`.
- **Allowed source modalities:** `VOICE`, `MANUAL`.
- **Expected target types:** Question, object, or current scene.
- **AI interpretation allowed:** Yes for requests that generate a new explanation.
- **Deterministic execution possible:** Partially. Revealing an already prepared hint or step is deterministic; generating new explanation is not.
- **Teacher approval may be required:** Yes when generating a new public explanation.
- **Public mutation possible:** Yes after validation and approval policy.
- **Expected failure modes:** `GENERATION_UNAVAILABLE`, `VALIDATION_FAILURE`, `CURRICULUM_UNAVAILABLE`, `STALE_TARGET`, `AMBIGUOUS_REFERENCE`.

#### `DICTATE`

- **Purpose:** Convert spoken teacher dictation into structured board content.
- **Allowed actors:** `TEACHER`.
- **Allowed source modalities:** `VOICE`.
- **Expected target types:** Current scene or a free-canvas insertion point.
- **AI interpretation allowed:** Yes. Speech-to-text and structured-content mapping are AI-mediated.
- **Deterministic execution possible:** Partially. Recognition is nondeterministic; final structured placement is deterministic once resolved.
- **Teacher approval may be required:** Yes when confidence is low or the dictated content is answer-like and would otherwise leak privately.
- **Public mutation possible:** Yes after validation.
- **Expected failure modes:** `LOW_CONFIDENCE`, `AMBIGUOUS_REFERENCE`, `VALIDATION_FAILURE`, `UNSUPPORTED_OFFLINE_ACTION`.

#### `ASK`

- **Purpose:** Answer a teacher question privately without changing learner-facing content.
- **Allowed actors:** `TEACHER`.
- **Allowed source modalities:** `VOICE`, `MANUAL`.
- **Expected target types:** Current scene, active object, or no target.
- **AI interpretation allowed:** Yes.
- **Deterministic execution possible:** No for natural-language answers; deterministic math lookup is possible when the question is a direct known answer.
- **Teacher approval may be required:** No. Result is private by default.
- **Public mutation possible:** No by default. A separate `PRESENTATION_CONTROL` action is required to make an answer public.
- **Expected failure modes:** `UNRESOLVED_REFERENCE`, `AMBIGUOUS_REFERENCE`, `GENERATION_UNAVAILABLE`, `VALIDATION_FAILURE`.

#### `NAVIGATE`

- **Purpose:** Move the classroom to a specific prepared scene.
- **Allowed actors:** `TEACHER`, `DISPLAY`.
- **Allowed source modalities:** `MANUAL`, `VOICE`, `TOUCH`, `PREPARED_LESSON`, `SYSTEM_RECOVERY`.
- **Expected target types:** Scene identity or positional reference such as next/previous.
- **AI interpretation allowed:** Yes for natural-language references.
- **Deterministic execution possible:** Yes once the target scene identity is resolved.
- **Teacher approval may be required:** No.
- **Public mutation possible:** Yes.
- **Expected failure modes:** `MISSING_TARGET`, `STALE_TARGET`, `INVALID_SESSION_STATE`, `UNSUPPORTED_OFFLINE_ACTION`.

#### `PRESENTATION_CONTROL`

- **Purpose:** Reveal or hide hints, answers, solution steps, or scene elements.
- **Allowed actors:** `TEACHER`, `DISPLAY`.
- **Allowed source modalities:** `MANUAL`, `VOICE`, `TOUCH`, `PREPARED_LESSON`.
- **Expected target types:** Scene element, reveal group, or question-package component.
- **AI interpretation allowed:** Yes for natural-language references.
- **Deterministic execution possible:** Yes once target and absolute desired state are resolved.
- **Teacher approval may be required:** No.
- **Public mutation possible:** Yes.
- **Expected failure modes:** `STALE_TARGET`, `NO_OP` when already in requested state, `INVALID_SESSION_STATE`, `UNSUPPORTED_OFFLINE_ACTION`.

#### `CANVAS_CONTROL`

- **Purpose:** Create or manipulate digital ink on the annotation layer.
- **Allowed actors:** `TEACHER`, `DISPLAY`.
- **Allowed source modalities:** `TOUCH`, `STYLUS`, `MANUAL`.
- **Expected target types:** Annotation layer, stroke identity, or annotation object identity.
- **AI interpretation allowed:** No. Ink operations are deterministic.
- **Deterministic execution possible:** Yes.
- **Teacher approval may be required:** No, but destructive `clear` requires explicit confirmation.
- **Public mutation possible:** Yes.
- **Expected failure modes:** `BASELINE_CONFLICT`, `STALE_TARGET`, `UNSUPPORTED_OFFLINE_ACTION`, `JOURNAL_LIMIT`.

#### `ASSESS`

- **Purpose:** Request interpretation and deterministic validation of selected student or teacher work.
- **Allowed actors:** `TEACHER`.
- **Allowed source modalities:** `VOICE`, `TOUCH`, `EXPLICIT_ASSESSMENT_REQUEST`.
- **Expected target types:** Selected ink, answer object, or explicit object identity.
- **AI interpretation allowed:** Yes for handwriting interpretation; deterministic math validation follows.
- **Deterministic execution possible:** Partially. Handwriting interpretation is AI; math validation is deterministic.
- **Teacher approval may be required:** No. Result is private to the teacher by default.
- **Public mutation possible:** No by default. Revealing assessment publicly requires a separate `PRESENTATION_CONTROL` action.
- **Expected failure modes:** `INSUFFICIENT_INK`, `VALIDATION_FAILURE`, `GENERATION_UNAVAILABLE`, `UNSUPPORTED_OFFLINE_ACTION`.

#### `SESSION_CONTROL`

- **Purpose:** Change session lifecycle or device authority.
- **Allowed actors:** `TEACHER`, `SYSTEM`.
- **Allowed source modalities:** `MANUAL`, `VOICE`, `SYSTEM_RECOVERY`.
- **Expected target types:** Session lifecycle reference or device-authority reference.
- **AI interpretation allowed:** No for lifecycle transitions; voice MAY be interpreted to identify the intent.
- **Deterministic execution possible:** Yes.
- **Teacher approval may be required:** No, but termination and destructive authority changes require explicit confirmation.
- **Public mutation possible:** Session-level; does not directly alter a scene.
- **Expected failure modes:** `INVALID_SESSION_STATE`, `STALE_REVISION`, `STALE_DISPLAY_EPOCH`, `UNAUTHORIZED`, `UNSUPPORTED_OFFLINE_ACTION`.

#### `MEDIA_CONTROL`

- **Purpose:** Control AI voice output or other learner-observable media.
- **Allowed actors:** `TEACHER`.
- **Allowed source modalities:** `MANUAL`, `VOICE`.
- **Expected target types:** Media or audio-playback reference.
- **AI interpretation allowed:** No.
- **Deterministic execution possible:** Yes.
- **Teacher approval may be required:** No.
- **Public mutation possible:** Yes, affecting learner-observable playback state.
- **Expected failure modes:** `MEDIA_UNAVAILABLE`, `INVALID_SESSION_STATE`, `STALE_REVISION`.

## 7. Source Modality Mapping

### 7.1 Modality Definitions

The `sourceModality` enum is:

- `MANUAL`
- `VOICE`
- `TOUCH`
- `STYLUS`
- `PREPARED_LESSON`
- `SYSTEM_RECOVERY`
- `EXPLICIT_ASSESSMENT_REQUEST`

### 7.2 Modality to TeachingAction Mapping

| Source | Construction path | AI interpretation required? | Deterministic construction allowed? | Notes |
|---|---|---|---|---|
| `MANUAL` | Controller manual buttons or controls construct the action directly | No | Yes | Primary fallback when voice or AI is unavailable |
| `VOICE` | Push-to-talk audio is interpreted into a structured `TeachingAction` candidate by the AI boundary | Yes | No | LLM output is untrusted; raw audio is not persisted by default |
| `TOUCH` | Direct touch selection or manipulation produces an explicit target action | No | Yes | Share one interaction model with mouse |
| `STYLUS` | Stylus writing or explicit draw/select mode produces deterministic ink or selection actions | No | Yes | Smart-stylus behavior is opportunistic; explicit mode remains fallback |
| `PREPARED_LESSON` | Cached lesson navigation and reveal actions are constructed deterministically | No | Yes | Eligible for offline provisional execution only within the allowlist |
| `SYSTEM_RECOVERY` | Backend or recovered client constructs recovery, resync, or authority actions | No | Yes | `SYSTEM` actor; MUST NOT be triggered by untrusted client payload |
| `EXPLICIT_ASSESSMENT_REQUEST` | Teacher explicitly requests ink assessment; AI interpretation follows | Yes | No | Online-only; result is private to the teacher by default |

### 7.3 Rules

- Voice interpretation MUST produce a versioned structured `TeachingAction` candidate and MUST NOT mutate state directly.
- Manual, touch, stylus, and prepared-lesson paths SHOULD construct deterministic actions without AI when the target and absolute state are already explicit.
- The producing client MAY delegate AI interpretation, but the submitted action remains a candidate until the Session Core accepts it.
- Raw audio, raw handwriting bitmaps, and model-internal interpretation artifacts are not part of the canonical `TeachingAction` envelope.

## 8. Reference Resolution and Target Model

### 8.1 Locked Resolution Priority

The Session Core resolves natural or indirect references in the locked order:

```text
Explicit selection
      ↓
Active object
      ↓
Current scene
      ↓
Last modified object
      ↓
Last generated object
      ↓
Recent teaching history
```

This priority MUST NOT be reordered by a client, an LLM, or a voice interpreter.

### 8.2 Target Model

A `target` MAY carry:

- an explicit stable object or scene identity;
- a positional reference such as `NEXT`, `PREVIOUS`, or `CURRENT`;
- a natural-language reference token to be resolved;
- a candidate set when the interpretation boundary is uncertain;
- a target-kind and target-lineage precondition.

The authoritative `resolvedTarget` records the resolved stable identity and its current lineage after backend resolution.

### 8.3 Resolution States

| State | Meaning | Required behavior |
|---|---|---|
| `UNRESOLVED_TARGET` | No resolvable target was supplied but the intent requires one | Reject with `UNRESOLVED_REFERENCE`; no canonical mutation |
| `CANDIDATE_TARGET` | One or more possible targets were proposed | Backend resolves using the locked priority and canonical context |
| `RESOLVED_TARGET` | Exactly one authoritative target was resolved | Proceed to constraint and policy validation |
| `MATERIALLY_AMBIGUOUS_TARGET` | Multiple plausible targets remain after priority resolution | Reject with `AMBIGUOUS_REFERENCE`; request private clarification; never guess |
| `MISSING_TARGET` | The referenced identity does not exist in canonical state | Reject with `UNRESOLVED_REFERENCE`; no mutation |
| `STALE_TARGET` | The identity exists but its lineage or preconditions no longer match | Reject with `STALE_TARGET`; resync or reselect |

### 8.4 Ambiguity Rules

- The backend MUST NOT allow an LLM to silently guess when material ambiguity remains.
- Material ambiguity triggers a private teacher clarification request with candidate alternatives.
- A clarification request is not a canonical mutation; it carries the original `actionId` as `causationId` for the follow-up action.
- A follow-up action with an explicit target is a new `TeachingAction` with a new `actionId` and its own idempotency identity.

## 9. Revision, Idempotency, and Replay Integration

### 9.1 Expected Revision

- Normal online mutations require `expectedSessionRevision` equal to the current canonical revision.
- A mismatch is `STALE_REVISION` and produces a resynchronization instruction.
- The Session Core MUST NOT silently rebase a stale online action.
- Reads and snapshot requests do not require an expected mutation revision.

### 9.2 Stale Revision

- `STALE_REVISION` means the client must obtain a full role-specific snapshot and recompose the action.
- The failed action creates no revision and no journal entry.
- The client MAY resubmit after resync with a new `actionId` or, if the previous outcome is unknown, retry the original idempotency identity.

### 9.3 Duplicate Action

- Two actions with the same `actionId` are distinct from two actions with the same `idempotencyKey`.
- A duplicate `actionId` with different content is malformed and MUST be security-auditable.
- A duplicate `idempotencyKey` with the same binding returns the original outcome.

### 9.4 Duplicate Idempotency Key

- Exact binding: return the original authoritative outcome and original accepted revision; no re-execution; no revision.
- Conflicting binding: reject with `IDEMPOTENCY_CONFLICT`; no mutation; MUST be security-auditable.
- Idempotency lookup occurs before current-revision rejection so a lost response can be recovered even after the session advanced.

### 9.5 Retry Behavior

- Unknown outcome after a possible commit: retry the original idempotency identity.
- Known rejection with a terminal category: do not blindly retry; resolve the underlying cause first.
- Transport or timeout failure: retryable using the same identity.
- Stale revision or stale epoch: resynchronization-required, not a simple retry.

### 9.6 Expiration and Replay Protection

- `createdAt` and `expiresAt` provide bounded replay protection.
- An expired action is rejected before idempotency and revision evaluation.
- The backend MAY shorten the requested expiry according to intent-specific policy.
- Clock skew MUST NOT grant authority or bypass expiry.

### 9.7 Display Epoch Validation

- Display-authority actions carry `displayEpoch`.
- A mismatch with the current canonical epoch is `STALE_DISPLAY_EPOCH`.
- Old-epoch actions never mutate canonical state and never silently rebase.
- Exact retries of previously accepted old-epoch commands return their recorded outcome after authentication.

### 9.8 Action Ordering

- The Session Core serializes mutations per session.
- Actions are accepted in the order the Session Core serializes them, not the order a client claims.
- One canonical mutation consumes exactly one revision increment when accepted.

### 9.9 Reconnect Resubmission

- On reconnect, a client requests a full role-specific snapshot and resynchronizes before resubmitting stale actions.
- Actions with unknown outcome are retried using their original idempotency identity.
- Offline provisional operations are submitted through the reconciliation path defined in V0.2, not as ordinary online actions.

### 9.10 Failure Classification

| Class | Meaning | Example categories |
|---|---|---|
| `RETRYABLE` | Transient or unknown-outcome failure | transport loss, timeout, unknown commit outcome |
| `REJECTED` | Action is invalid for policy, state, or target reasons | malformed, unauthorized, forbidden, invalid session state |
| `RESYNCHRONIZATION_REQUIRED` | Client context is stale and must be refreshed | stale revision, stale epoch, revision gap |
| `TERMINAL` | Reuse or version state makes retry meaningless | expired, idempotency conflict, unsupported version, duplicate conflict |

## 10. Execution Classification

### 10.1 Classification Dimensions

Every accepted action is classified by three independent dimensions:

1. **Latency:** `IMMEDIATE` or `ASYNC`.
2. **Gating:** none, `APPROVAL_GATED`, `VALIDATION_GATED`, or both.
3. **Connectivity:** `ONLINE_ONLY` or `OFFLINE_ELIGIBLE`.

The requested classification dimensions combine into the following architectural classes:

### 10.2 Classes

#### A. Deterministic Immediate Actions

- **Rule:** Fully validated synchronously and committed in one mutation without AI generation.
- **Examples:** navigation to a resolved scene, reveal/hide to an absolute state, deterministic presentation control.
- **Gates:** Session-state, authorization, revision, epoch, target, and visibility validation.
- **Connectivity:** Online; a defined subset is offline-eligible.

#### B. Asynchronous Generative Actions

- **Rule:** Enter an AI workflow; the public scene remains unchanged until atomic publication.
- **Examples:** generate question, modify explanation semantically, generate new scene.
- **Gates:** Validation, curriculum grounding, renderer compatibility, and approval when required.
- **Connectivity:** Online-only for new workflow creation.

#### C. Approval-Gated Actions

- **Rule:** Validated result is held privately until teacher approval and publication-time revalidation.
- **Examples:** generative actions in `APPROVAL` mode, answer-like public dictation, low-confidence public generation.
- **Gates:** Approval evidence plus all validation gates at publication.
- **Connectivity:** Online-only.

#### D. Validation-Gated Actions

- **Rule:** Cannot become public until deterministic or semantic validation succeeds, regardless of mode.
- **Examples:** any mathematical claim, curriculum assertion, or renderer-incompatible candidate.
- **Gates:** Required validation fails closed; the prior safe scene remains visible.
- **Connectivity:** Online-only for new semantic content.

#### E. Offline-Eligible Provisional Actions

- **Rule:** May execute locally during degraded connectivity under the V0.2 allowlist and later reconcile.
- **Examples:** cached-scene navigation, absolute reveal/hide, pen/highlighter strokes, targeted erase, local undo/redo, confirmed clear-ink.
- **Gates:** Prior verified package, current epoch, valid last safe snapshot, local journal integrity.
- **Connectivity:** Provisional locally; canonical only after reconciliation.

#### F. Online-Only Actions

- **Rule:** Cannot execute provisionally and are rejected or unavailable while offline.
- **Examples:** AI generation, cloud speech interpretation, handwriting assessment, pairing, replacement, approval, publication, pause, resume, termination.
- **Gates:** Full online authority, revision, epoch, and lifecycle checks.
- **Connectivity:** Online-only.

### 10.3 Example Mapping

| Example action | Class | Notes |
|---|---|---|
| Next scene | A online; E when display degraded | Target normalized to explicit scene identity |
| Previous scene | A online; E when display degraded | Target normalized to explicit scene identity |
| Reveal hint | A online; E when display degraded | Absolute desired reveal state |
| Hide answer | A online; E when display degraded | Absolute desired hide state |
| Clear ink | A with confirmation; E when display degraded | Baseline conflict prevents silent deletion |
| Generate question | B + D; C in Approval Mode | Action enters workflow; publication is separate |
| Modify explanation | B + D; C when generative | Dependency revalidation at publication |
| Assess selected work | F + D | Online-only; private result by default |
| Start session | A + F | Lifecycle and display-verification gates |
| End session | A + F with confirmation | Destructive; offline forbidden |

## 11. Auto Versus Approval Mode

### 11.1 Approval Categories

| Category | Behavior |
|---|---|
| Never requires approval | Deterministic navigation, presentation reveal/hide, non-destructive ink operations, private `ASK`, `ASSESS`, `MEDIA_CONTROL` |
| May require approval | Safe generative actions in `AUTO` mode with high confidence and all validation gates passing |
| Always requires approval | Generative actions in `APPROVAL` mode, low-confidence or materially ambiguous public content, answer-like public dictation, destructive actions requiring confirmation |

### 11.2 Mode Interaction

- `AUTO` relaxes only the human approval gate. It NEVER bypasses deterministic validation, curriculum grounding, visibility policy, or destructive confirmation.
- `APPROVAL` holds validated public-facing candidates privately until the teacher approves the exact candidate hash.
- The effective mode for an action is the teacher-selected `executionMode`, further constrained by intent policy, validation outcome, and ambiguity.

### 11.3 Confidence and Ambiguity Interaction

- Low confidence or material ambiguity forces private clarification or `APPROVAL`-style review; it MUST NOT produce silent public content.
- Confidence is advisory and does not certify correctness.
- Validation failure blocks publication in both modes.

### 11.4 Visibility While Pending

- Pending generative candidates remain `PRIVATE_TEACHER`.
- The learner-facing display remains on the last complete valid public scene.
- Intermediate generation progress is never sent to the display.

## 12. Security and Authorization

Authorization is a backend responsibility. A client-constructed `TeachingAction` MUST NOT be trusted merely because it is well-formed.

### 12.1 Authorization Layers

| Layer | Rule |
|---|---|
| Actor authentication | The actor identity MUST come from the authenticated principal, not from the action body |
| Session membership | The actor MUST be authorized for the referenced session |
| Controller grant | Controller mutation authority MUST be current and unforged |
| Display grant | Display authority MUST be current and carry the correct epoch |
| Display epoch | Old-epoch actions MUST be fenced |
| Role restriction | The `actorRole` MUST be allowed for the requested intent |
| Intent-level authorization | The intent MUST be permitted in the current session lifecycle |
| Target-level authorization | The resolved target MUST be within the actor's permitted scope |

### 12.2 Untrusted AI Candidates

- LLM-generated `TeachingAction` candidates are untrusted structured input.
- They MUST NOT carry executable markup, raw audio, credentials, or authoritative state.
- The AI boundary cannot publish directly to the display.
- Every field is revalidated by the Session Core before acceptance.

## 13. Visibility

### 13.1 Visibility Enumeration

- `PUBLIC`: learner-facing classroom display projection.
- `PRIVATE_TEACHER`: teacher-controller projection only.
- `SYSTEM`: system-only, never projected to either classroom surface.

### 13.2 Requested, Authorized, and Resulting Visibility

- **Requested visibility** is the client's desired classification.
- **Authorized visibility** is computed by the Session Core from intent, target, policy, and current session state.
- **Resulting projection visibility** is the independently built role-specific projection that actually reaches a surface.

### 13.3 Visibility Rules

- Client-requested visibility MUST NOT override server policy.
- Answers and assessment results default to `PRIVATE_TEACHER` even if requested as `PUBLIC`.
- Making a private answer public requires a separate `PRESENTATION_CONTROL` action.
- `SYSTEM` visibility is reserved for backend-only state such as pairing challenges, credentials, raw AI material, and raw audio.
- A display projection is built independently and MUST NOT contain private fields hidden by the client.

## 14. Validation Pipeline

### 14.1 Logical Stages

The Session Core evaluates an action in this order:

1. **Contract/schema validation** — envelope shape, supported version, size limits.
2. **Authentication** — verify actor identity from the authentication boundary.
3. **Authorization** — session membership, role, controller grant, display grant, epoch.
4. **Session-state validation** — lifecycle and prepared-package constraints.
5. **Revision validation** — `expectedSessionRevision` check.
6. **Display-epoch validation** — where display authority is applicable.
7. **Intent validation** — intent recognized and permitted for role and state.
8. **Reference resolution** — resolve target, detect ambiguity or staleness.
9. **Constraint validation** — intent-specific constraints and preconditions.
10. **Policy/visibility validation** — requested visibility, execution mode, confirmation requirement.
11. **Execution classification** — classify as immediate, async, approval-gated, validation-gated, offline-eligible, or online-only.
12. **Idempotency lookup and commit** — idempotency resolution occurs before current-revision rejection, then the complete next snapshot and journal entry commit atomically.

### 14.2 Generative Action Distinction

Action validation only proves the command is acceptable. For generative actions, the produced `TeachingScene` or `QuestionPackage` undergoes a separate validation lifecycle:

- schema and semantic validation;
- curriculum grounding;
- deterministic mathematics validation;
- renderer compatibility;
- candidate hash assignment;
- approval, when required;
- one atomic publication commit.

Action validation failure rejects the command. Candidate validation failure preserves the last safe scene and repairs or regenerates privately.

## 15. Error Model

### 15.1 Error Categories

| Category | Meaning | Teacher-facing response | Client recovery instruction | Diagnostic/system detail |
|---|---|---|---|---|
| `MALFORMED_ACTION` | Envelope or schema invalid | Friendly "perintah tidak dikenali" message | Reconstruct the action | Full validation path internally |
| `UNSUPPORTED_CONTRACT_VERSION` | Unknown contract version | Version-compatibility message | Request compatible contract or read-only recovery | Contract version and supported range |
| `UNAUTHORIZED` | Actor lacks session or authority | "Anda tidak memiliki akses" | Re-authenticate or restore authority | Actor, role, session, authority lineage |
| `FORBIDDEN_INTENT` | Intent not allowed in current state or role | Clear refusal with reason | Change state or use permitted action | Intent, role, lifecycle state |
| `INVALID_SESSION_STATE` | Lifecycle does not permit the action | State-aware guidance | Resync or use appropriate lifecycle action | Current state and required state |
| `STALE_REVISION` | Expected revision does not match | "Konteks berubah" | Request full role-specific snapshot | Expected and current revision |
| `STALE_DISPLAY_EPOCH` | Display authority is old | Read-only/replacement notice | Re-pair or resync display | Submitted and current epoch |
| `IDEMPOTENCY_CONFLICT` | Key reused with changed binding | Generic retry guidance | Generate a new key for new content | Conflict binding digest only |
| `DUPLICATE_ACTION` | Duplicate action identity or effect detected | Already-done confirmation | No action required | Original outcome reference |
| `EXPIRED_ACTION` | Action expired | "Permintaan kedaluwarsa" | Resubmit with fresh expiry | Created and expiry timestamps |
| `UNRESOLVED_REFERENCE` | Target missing or not resolvable | "Target tidak ditemukan" | Reselect target or resync | Reference and resolution state |
| `AMBIGUOUS_REFERENCE` | Materially ambiguous target | Private clarification request with alternatives | Select one alternative | Candidate set and resolution priority |
| `UNSUPPORTED_OFFLINE_ACTION` | Action is online-only while offline | Degraded-mode guidance | Reconnect and resubmit | Intent and connectivity state |
| `VALIDATION_FAILURE` | Deterministic or semantic validation failed | Private validation-failure notice | Correct request or keep prior scene | Validation evidence class only |
| `GENERATION_UNAVAILABLE` | AI or deterministic generation unavailable | "Fitur tidak tersedia" | Retry later or use manual fallback | Availability scope |
| `BUSY_WORKFLOW` | A public-scene workflow is already active | "Masih memproses permintaan" | Wait or cancel pending workflow | Workflow state |
| `TIMEOUT` | Workflow or action exceeded policy | Timeout notice | Retry or resync | Timeout policy class |
| `PRECONDITION_FAILED` | Target lineage or dependency changed | "Target sudah berubah" | Resync and reselect | Precondition and current lineage |

### 15.2 Error Projection Rules

- Teacher-facing errors MUST be concise, non-technical, and actionable.
- Recovery instructions MUST be role-appropriate.
- Diagnostic/system detail MUST NOT reach the classroom display.
- Display errors MUST NOT expose teacher-private content, internal AI prompts, candidate data, credentials, or sensitive validation details.

## 16. Examples and Counterexamples

### 16.1 Deterministic Manual Action

```text
contractName: TeachingAction
contractVersion: 0.1
actionId: "a_01"
idempotencyKey: "ik_01"
sessionId: "s_01"
actorId: "teacher_01"
actorRole: TEACHER
sourceModality: MANUAL
intent: PRESENTATION_CONTROL
target: { identity: "scene_03", element: "hint_1" }
constraints: { reveal: true }
visibility: PUBLIC
executionMode: AUTO
expectedSessionRevision: 12
createdAt: "..."
expiresAt: "..."
authorityLineage: "ctl_v7"
```

Result: hint 1 on scene 3 becomes visible in one deterministic commit.

### 16.2 Voice-Derived Action

Teacher says: "Tampilkan pembahasannya langkah demi langkah."

The AI boundary produces a `PRESENTATION_CONTROL` candidate targeting the active question package's solution-step group with an absolute reveal sequence. The Session Core resolves the target and applies the allowed step state.

### 16.3 Ambiguous Voice Command

Teacher says: "Ubah yang kedua."

The AI boundary cannot resolve "yang kedua" unambiguously. The action is not guessed. The Session Core returns `AMBIGUOUS_REFERENCE` with a private clarification request listing candidate objects.

### 16.4 Generative Question Request

Teacher says: "Buat satu soal seperti tadi tapi sedikit lebih sulit."

The action is `GENERATE` with constraints `difficulty: INCREASE_ONE_LEVEL`, `topic: INHERIT`, and `grade: INHERIT`. The Session Core accepts an async workflow and leaves the current public scene unchanged.

### 16.5 Approval-Gated Generation

In `APPROVAL` mode, the validated question candidate remains `PRIVATE_TEACHER`. The teacher approves the exact candidate hash; publication-time revalidation succeeds; one atomic commit publishes the complete scene.

### 16.6 Stale Revision

A controller submits a navigation action with `expectedSessionRevision: 12` while the canonical revision is 13. The Session Core rejects with `STALE_REVISION` and a resync instruction.

### 16.7 Duplicate Request

The same `GENERATE` action is retried after a lost response with the same `idempotencyKey` and binding. The Session Core returns the original workflow-accepted outcome without creating a second workflow.

### 16.8 Replaced-Display Action

An old display submits a provisional `CANVAS_CONTROL` with `displayEpoch: 1` after replacement moved the canonical epoch to 2. The Session Core rejects with `STALE_DISPLAY_EPOCH`; the journal is quarantined.

### 16.9 Offline Provisional Action

An active display loses connectivity and performs a confirmed clear-ink operation locally. It records a normalized absolute `CANVAS_CONTROL` operation with its base revision and epoch in the provisional journal. On reconnect, reconciliation submits the journal and returns per-operation outcomes.

### 16.10 Forbidden Action

A display attempts `GENERATE` while offline. The action is outside the offline allowlist and is rejected as `UNSUPPORTED_OFFLINE_ACTION`. A controller attempting `ASSESS` while the session is `PAUSED` is rejected as `INVALID_SESSION_STATE`.

## 17. Contract Evolution

### 17.1 Versioning

- `TeachingAction` versions are semantic and monotonic.
- The contract version is carried in every action.
- Unknown versions are rejected before business processing.

### 17.2 Backward Compatibility

- Additive optional fields MAY be introduced in a backward-compatible minor version.
- Existing required field semantics MUST NOT change without a breaking version.
- New enum values MUST follow a defined unknown-value policy: unknown values are rejected unless a later decision explicitly permits forward-compatible enums.

### 17.3 Breaking Changes

Breaking changes include:

- removing or renaming a required field;
- changing a field's type or required cardinality;
- changing the meaning of an existing intent;
- changing the authority or visibility semantics of an existing field.

Breaking changes require a new major contract version and migration planning.

### 17.4 Intent Evolution

- Adding an intent is an additive change only if the new intent cannot be confused with an existing intent.
- Repurposing an existing intent is breaking.
- No new intent is introduced in V0.3; any required future intent must pass the locked product-discovery decision process.

### 17.5 Field Deprecation

- A field MAY be deprecated by a minor version while remaining accepted for backward compatibility.
- Deprecated fields MUST document a removal version.
- The backend MUST NOT silently reinterpret a deprecated field.

### 17.6 Mixed-Client-Version Handling

- The Session Core advertises its supported contract versions.
- A client using an unsupported version becomes read-only on its last safe projection and requests a compatible recovery path.
- A mixed-version environment MUST NOT weaken canonical invariants or permit a stale client to mutate with an old version silently.

## 18. Invariants

1. Every `TeachingAction` has a stable `actionId` and, for mutations, a stable `idempotencyKey`.
2. Canonical classroom state changes only through an accepted action processed by the backend Session Core.
3. Duplicate actions cannot duplicate canonical effects.
4. Stale display authority cannot mutate canonical state.
5. Materially ambiguous references are never guessed.
6. Requested visibility cannot bypass authorization or server visibility policy.
7. AI candidates are never authoritative.
8. Rejected actions do not mutate canonical state and do not consume a revision.
9. Generative actions cannot partially publish a scene.
10. Action processing integrates with monotonic session revision: each accepted canonical mutation increments revision exactly once.
11. Idempotency resolution occurs before current-revision rejection for uncertain-outcome recovery.
12. The display never receives private teacher data, credentials, pairing secrets, raw audio, or internal AI material through an action result.

## 19. Testable Acceptance Criteria

### 19.1 Schema Validation

1. A missing required field is rejected as `MALFORMED_ACTION`.
2. An unknown `contractName` or unsupported `contractVersion` is rejected before business logic.
3. A client-supplied `resolvedTarget` is ignored or rejected; only backend resolution is authoritative.
4. Unknown constraints are rejected or ignored only under a defined additive-version rule.

### 19.2 Intent Behavior

5. Every locked intent maps to a handler and a lifecycle eligibility rule.
6. An unknown intent is rejected without mutation.
7. A role/state intent mismatch is rejected as `FORBIDDEN_INTENT` or `INVALID_SESSION_STATE`.

### 19.3 Idempotency

8. Exact retry with the same binding returns the original outcome and revision.
9. Reusing an idempotency key with changed binding fails with `IDEMPOTENCY_CONFLICT`.
10. A lost-response retry recovers the original outcome without re-execution.

### 19.4 Revision Concurrency

11. `STALE_REVISION` is returned when expected and current revisions differ.
12. A stale action never silently rebases.
13. Two serialized actions with the same expected revision are accepted in serialization order; the second becomes stale after the first commits.

### 19.5 Reference Resolution

14. Resolution follows the locked priority order.
15. `MATERIALLY_AMBIGUOUS_TARGET` triggers a clarification request and never a guess.
16. `MISSING_TARGET` and `STALE_TARGET` are rejected without mutation.

### 19.6 Authorization

17. An unauthorized actor is rejected before target resolution.
18. A display action with an old epoch is rejected as `STALE_DISPLAY_EPOCH`.
19. A controller action with a revoked authority lineage is rejected as `UNAUTHORIZED`.

### 19.7 Display Replacement

20. A replaced display cannot mutate canonical state.
21. Old-epoch provisional journals are quarantined, not merged.

### 19.8 Retry

22. Retryable, rejected, resynchronization-required, and terminal classes are distinguishable.
23. Expired actions are rejected before idempotency and revision checks.

### 19.9 Ambiguity Handling

24. Low-confidence or ambiguous public actions do not reach the display.
25. A follow-up action resolving ambiguity carries the correct `causationId`.

### 19.10 Offline Behavior

26. Offline-eligible actions normalize relative operations to explicit targets or absolute states.
27. Online-only actions are rejected while degraded.
28. Provisional operations do not claim a canonical revision until reconciliation.

### 19.11 Auto/Approval Behavior

29. `AUTO` never bypasses validation, curriculum, visibility, or destructive confirmation.
30. `APPROVAL` holds candidates privately until exact-hash approval.
31. Validation failure blocks publication in both modes.

### 19.12 Public/Private Isolation

32. `PUBLIC`, `PRIVATE_TEACHER`, and `SYSTEM` results reach only the correct projection.
33. A private answer does not become public without a separate `PRESENTATION_CONTROL` action.
34. Negative projection tests prove private fields never reach the display.

## 20. Decisions Requiring Product Approval

The following decisions are not resolved by the locked inputs. Each item is presented with options, impact, recommendation, rationale, and whether it blocks V0.3 lock.

### 20.1 Confidence and Ambiguity Policy

**Question**
What confidence representation and policy may gate `AUTO` publication, and which ambiguity cases require mandatory clarification?

**Available options**

1. Treat confidence as advisory only; gate `AUTO` solely on deterministic validation and non-destructive intent.
2. Use qualitative bands (`LOW`, `MEDIUM`, `HIGH`) with policy per intent.
3. Use a numeric `0..1` threshold with an explicit product floor.
4. Hybrid: qualitative band for teacher display plus numeric evidence, with a policy floor.

**Architecture impact**

- Determines the `confidence` field's usable form and the Auto/Approval publication rule.
- Affects how low-confidence voice actions are handled.

**Recommended option**
Hybrid representation: qualitative band for teacher-facing display plus bounded numeric evidence; do not lock a numeric floor in V0.3. Treat confidence as advisory evidence; publication always requires all deterministic validation gates.

**Recommendation rationale**
It keeps teacher-facing clarity, preserves evidence for future policy, and avoids inventing an unapproved threshold. The contract remains implementable without the policy number.

**Blocks V0.3 lock:** No. The field and fail-safe behavior are defined; only the numeric policy floor is deferred.

### 20.2 Action Expiry Policy

**Question**
Which expiry model should govern `expiresAt` for ordinary teaching actions, approval-pending actions, and pairing/security actions?

**Available options**

1. One session-bounded default for all actions.
2. Intent-specific expiry classes.
3. Fixed short expiry for all mutations.
4. Context-sensitive expiry with authority and lineage changes invalidating approval.

**Architecture impact**

- Defines replay windows and cleanup policy.
- Interacts with V0.2 decision 33.5 on approval expiry.

**Recommended option**
Use expiry classes: session-bounded default for ordinary actions, context-sensitive approval expiry per V0.2 33.5, and short security-sensitive expiry for pairing/authority actions.

**Recommendation rationale**
It balances usability, replay protection, and the already-flagged context-sensitive approval behavior without choosing numeric durations.

**Blocks V0.3 lock:** No. Expiry categories are defined; numeric durations remain policy parameters.

### 20.3 Confidence and Ambiguity Retention

**Question**
Should voice-derived `confidence` and `ambiguity` metadata be persisted, aggregated for diagnostics, or treated as transient operational data only?

**Available options**

1. Transient only; never persisted.
2. Persist bounded aggregates for diagnostics.
3. Persist per-action metadata under retention policy.
4. Teacher-controlled retention.

**Architecture impact**

- Affects snapshot/journal size and privacy surface.
- Connects to the locked raw-audio-not-persisted principle.

**Recommended option**
Treat `confidence` and `ambiguity` as transient by default; allow only bounded, non-audio diagnostics under a separately approved retention policy.

**Recommendation rationale**
It minimizes privacy risk and aligns with "persist recognized command and structured intent, not raw interaction detail" in Product Discovery V0.2.

**Blocks V0.3 lock:** No. The field lifecycle is defined as operational; persistence policy is deferred.

### 20.4 Voice-Derived Action Retention

**Question**
What portion of a voice-derived `TeachingAction` is retained in the command journal when raw audio is not persisted?

**Available options**

1. Store the fully resolved structured action and outcome.
2. Store only intent, resolved target, and canonical result.
3. Store a redacted summary suitable for audit.
4. Do not journal voice actions beyond the normal outcome record.

**Architecture impact**

- Determines journal auditability and privacy.
- Affects debugging of ambiguous voice behavior.

**Recommended option**
Store the resolved structured action and canonical outcome, but exclude raw audio, model-internal tokens, and unapproved intermediate fragments.

**Recommendation rationale**
It preserves auditability while honoring the locked audio-privacy constraint.

**Blocks V0.3 lock:** No. The default retention boundary is defined.
