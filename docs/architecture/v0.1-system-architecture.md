## 3. Architectural Drivers

The approved architecture is driven by the following requirements:

- The MVP must be testable using an ordinary laptop, monitor, mouse, and smartphone.
- The product is software-first and hardware-agnostic.
- The smartphone acts as the teacher controller; the classroom screen acts as the learner-facing display.
- The backend owns authoritative classroom-session state.
- Controller, display, backend, AI, curriculum, and validation boundaries are contract-first.
- Teacher intent is represented by versioned structured `TeachingAction` contracts.
- Learner-facing content is represented by versioned structured `TeachingScene` contracts.
- Arbitrary AI-generated HTML or executable display payloads are prohibited.
- AI output is a candidate, never authoritative state.
- Mathematics shown to learners must pass deterministic validation wherever validation is applicable.
- Curriculum assertions must be grounded in controlled and versioned curriculum data.
- Scene generation and publication must be atomic; partially generated scenes must never appear.
- Prepared lessons must remain locally available during temporary connectivity degradation.
- Essential classroom interaction must degrade safely rather than fail catastrophically.
- Student data collection must be minimized.
- Raw classroom audio must not be persisted by default.
- Reliability and predictable recovery are more important than infrastructure sophistication.
- MVP operational complexity must remain low.

## 4. Architecture Decision

Pendago will use a backend-authoritative classroom session represented by:

1. A **canonical session snapshot** containing the complete authoritative state at one monotonic revision.
2. An **ordered command journal** recording each accepted revision-producing command and its outcome.
3. **Role-specific projections** independently derived for the teacher controller and classroom display.
4. A **server-mediated realtime channel** used to deliver committed projections and revision notifications.
5. **Full snapshot resynchronization** as the recovery mechanism for revision gaps, reloads, replacement, corruption, and reconnect.
6. A constrained **display-local provisional journal** for approved degraded-connectivity actions.

The snapshot is the authoritative recovery object. The command journal provides ordering, idempotency evidence, auditability, diagnosis, and controlled reconciliation, but it is not required to reconstruct the entire session through unbounded replay during normal MVP operation.

## 6. Major Components

### 6.1 Teacher Controller

The controller captures teacher intent, displays private information, presents approval controls, and sends versioned commands. It does not own classroom state and must recover from the backend snapshot after reload or disconnect.

The controller must never assume that an unacknowledged command failed. It retries an unknown outcome using the original idempotency identity.

### 6.2 Classroom Display

The display renders only a public projection of validated structured scenes. It supports ordinary laptop and monitor operation with mouse input, while remaining compatible with touch, stylus, projector, TV, and interactive-board environments.

The display stores a verified prepared-lesson package and the most recent safe public snapshot. During temporary connectivity loss it may execute only an explicit local action allowlist and records those operations in a provisional journal.

### 6.3 Contract and Authority Edge

All commands pass through a common logical boundary responsible for:

- contract version and payload validation;
- authentication and role authorization;
- session binding;
- controller authority and display-epoch fencing;
- idempotency checks;
- expected-revision checks;
- replay and expiry protections;
- request-size and abuse limits.

### 6.4 Authoritative Session Core

The session core serializes mutations for each classroom session. It evaluates commands against the canonical snapshot, resolves explicit targets, enforces lifecycle and visibility rules, invokes required validators, computes a complete next snapshot, and commits the snapshot and journal entry atomically.

Clients cannot replace or merge the canonical snapshot directly.

### 6.5 Teaching Intelligence Boundary

The AI orchestration boundary converts permitted requests into structured candidates. It manages generation, repair, validation, timeout, staleness, and approval state.

AI output remains private until it passes all applicable contract, curriculum, mathematics, safety, visibility, and renderer checks. The AI boundary cannot publish directly to the display.

### 6.6 Deterministic Engines

Deterministic engines validate claims that must not depend solely on an LLM, including mathematical correctness, curriculum provenance, schema conformance, target lineage, and renderer compatibility.

When deterministic validation is required and cannot be completed, publication fails closed while the current stable scene remains visible.

### 6.7 Atomic Commit Boundary

Every accepted canonical mutation produces one new session revision. The next canonical snapshot and its ordered command-journal entry commit together or not at all.

Rejected commands, exact idempotent retries, reads, heartbeats, transient generation progress, and defined no-ops do not create revisions.

### 6.8 Projection and Realtime Edge

The backend constructs separate role-specific projections. Private state is never sent to the display and hidden client-side.

Realtime delivery notifies clients of committed revisions. A client that detects a gap, incompatible update, reload, corruption, or unknown state requests a full role-specific snapshot and applies it atomically.

## 7. Communication Flow

### 7.1 Normal Teaching Command

```text
Teacher input
    → controller creates versioned TeachingAction
    → authority, idempotency, revision and lifecycle checks
    → target and visibility resolution
    → deterministic validation or AI orchestration when required
    → complete next snapshot computed
    → snapshot and journal committed atomically
    → role-specific projections emitted
    → controller receives private result
    → display receives public result
```

### 7.2 AI-Assisted Scene Generation

```text
TeachingAction
    → authoritative session accepts generation workflow
    → AI produces structured candidate privately
    → schema and semantic validation
    → curriculum grounding
    → deterministic mathematics validation
    → renderer validation
    → approval when required
    → one atomic publication command
    → complete TeachingScene becomes canonical
    → public projection is delivered
```

The previously published scene remains unchanged throughout generation and validation.

### 7.3 Display Realtime Recovery

```text
revision notification
    → display checks expected revision
    → contiguous compatible update: apply atomically
    → gap or incompatibility: request full public snapshot
    → validate snapshot away from visible renderer
    → replace local canonical projection atomically
```

### 7.4 Degraded Connectivity and Reconciliation

```text
backend unavailable
    → display retains verified package and last safe snapshot
    → allowlisted local actions create provisional operations
    → connectivity returns
    → stop new provisional mutation
    → authenticate and verify display epoch
    → submit typed provisional journal
    → backend reconciles against current canonical snapshot
    → one atomic reconciliation commit, when accepted
    → per-operation outcomes plus full public snapshot
    → display applies snapshot atomically
```

The backend never accepts a client-uploaded snapshot as canonical truth.

## 8. Authoritative Classroom State

The canonical snapshot conceptually includes:

- session identity and monotonic revision;
- lifecycle state;
- owner and authorized classroom context;
- immutable lesson and curriculum versions;
- prepared-package identity and readiness;
- current scene, lesson position, reveal state, and target lineage;
- published generated and annotation layers;
- controller authority;
- active display and display epoch;
- active AI workflow and pending-approval references;
- validation and provenance references;
- lifecycle timestamps and termination reason.

Transport connections, heartbeat counters, AI progress percentages, pairing secrets, credentials, raw audio, and renderer-only temporary UI state are not canonical classroom state.

## 9. Session Revision and Command Journal

- The first persisted snapshot uses revision `1`; revision `0` represents no session.
- Each canonical mutation increments the revision exactly once.
- Commands are serialized within a session.
- Normal online mutation commands are evaluated against an expected revision.
- Stale online commands require resynchronization rather than silent rebasing.
- An idempotency identity is bound to session, actor, authority, command type, normalized payload, contract version, and applicable display epoch.
- Reusing the same identity with the same binding returns the original outcome.
- Reusing it with changed content or authority fails with an idempotency conflict.
- The journal records revision-producing commands and their authoritative outcomes.
- Operational logs may record rejected or no-op attempts separately, but those attempts are not canonical journal revisions.

The journal is intentionally narrower than a pure event-sourcing model. Normal recovery reads the current snapshot rather than replaying an unbounded event history.

## 10. Display Authority and Epoch

The `display_epoch` is a monotonic fencing token for writable display authority.

- It starts at `0` when no active display exists.
- Initial activation sets it to `1`.
- Same-display reload or reconnect does not increment it.
- Display replacement prepares a read-only candidate before cutover.
- Atomic cutover increments the epoch once, activates the candidate, and revokes the old display.
- At most one epoch may have mutation authority.
- Commands and provisional operations from an older epoch cannot mutate canonical state.
- Offline content from a replaced display is quarantined for explicit recovery and is never silently merged or discarded.

The backend cannot remotely blank a display that is fully offline. Epoch fencing protects canonical authority but cannot instantly change pixels on a disconnected physical device.

## 11. TeachingAction and TeachingScene Contracts

`TeachingAction` is a versioned structured representation of teacher intent. It carries explicit targets, visibility, preconditions, confirmation requirements, expected revision, authority context, and idempotency identity.

`TeachingScene` is a complete, versioned, learner-facing semantic scene. It has stable identity, integrity information, curriculum provenance when applicable, deterministic validation evidence when applicable, and renderer-compatible structured content.

Neither contract may carry arbitrary executable markup. Rendering behavior is defined by controlled application capabilities rather than generated code.

## 12. AI Orchestration Boundary

The AI system is an asynchronous candidate producer behind the authoritative session core.

An AI workflow is bound to:

- the session and originating command;
- source scene and target lineage;
- lesson and curriculum versions;
- semantic dependency fingerprint;
- TeachingAction and TeachingScene contract versions;
- candidate hash;
- visibility classification;
- validator evidence;
- approval requirement.

Candidate repair or regeneration changes the candidate hash and invalidates prior approval. Late, stale, timed-out, or post-termination results cannot mutate the session.

For the MVP, one public-scene-affecting generation workflow is permitted at a time. The architecture does not depend on a hidden generation queue.

## 13. Mathematics Validation

Mathematical expressions, answers, equivalence claims, transformations, examples, and generated question packages must pass deterministic validation wherever such validation is defined.

The LLM may propose content but may not certify mathematical correctness. Failed or unavailable required validation blocks publication and preserves the last safe scene.

Validation evidence must be traceable to the published scene or generated artifact without exposing unnecessary internal details to learners.

## 14. Curriculum Grounding

Sessions pin a controlled curriculum source version. Curriculum-sensitive generation and validation use that pinned version throughout the session.

Curriculum assertions must include controlled provenance. Model recollection, uncontrolled internet content, or prompt text alone cannot act as curriculum authority.

Changing curriculum versions during an active classroom session is outside the V0.1 architecture and requires a later explicit decision.

## 15. Offline and Degraded Connectivity

The architecture supports temporary degraded operation after a display has obtained:

- a verified prepared-lesson package;
- the latest safe public snapshot;
- valid display identity and last-known epoch;
- the contracts required for local rendering and allowlisted actions.

The MVP offline allowlist may include explicit cached-scene navigation, absolute reveal or hide state, pen and highlighter strokes, targeted erase, local undo and redo, confirmed local clear, and non-semantic renderer controls.

Offline operation excludes AI generation, cloud speech interpretation, handwriting assessment, pairing, replacement, curriculum changes, semantic scene generation, approval, publication, pause, resume, and termination.

Relative operations are normalized to explicit intent before journaling. For example, `next` becomes navigation to a specific scene identity, and `toggle` becomes an absolute desired state.

Cold-start offline classroom operation is not guaranteed by this architecture. The approved continuity objective is temporary degradation after successful online preparation and cache verification.

## 16. Authentication and Classroom Pairing

Teacher authority and device presence are separate concerns. A temporary controller disconnect does not revoke authority, pause the session, end the session, or increment revision.

Display pairing uses a short-lived, session-scoped, role-scoped, one-use, replay-resistant challenge with teacher confirmation. QR presentation and numeric fallback support the ordinary-device MVP. Numeric attempts require rate limiting.

Pairing does not itself grant writable authority. A candidate becomes active only through an authoritative atomic activation or replacement command.

For MVP, one controller holds mutation authority at a time. Controller takeover revokes or fences the previous authority before the new controller may mutate.

## 17. Persistence Model

The logical persistence model contains:

- the current canonical session snapshot;
- the ordered revision-producing command journal;
- command idempotency records;
- immutable lesson and curriculum version references;
- prepared-lesson package metadata and integrity information;
- validated scene and generated-artifact references;
- role and device authority metadata;
- retained recovery artifacts governed by explicit policy.

The model does not prescribe a database technology. Snapshot and journal atomicity is a required capability of whichever persistence technology is later selected.

Raw classroom audio is excluded from default persistence. Student identity is not required for the core classroom session.

## 18. Deployment and Operational Shape

The MVP should be deployable as a small number of logical runtime responsibilities:

- web delivery for controller and display surfaces;
- authoritative application and session processing;
- realtime projection delivery;
- asynchronous AI and validation work;
- durable snapshot, journal, curriculum, lesson, and package storage.

These are logical boundaries, not instructions to deploy separate services. The initial deployment should avoid distributed-system boundaries that are not needed for reliability, isolation, or asynchronous work.

Infrastructure sophistication, multi-region operation, independent microservices, specialized event platforms, and dedicated realtime clusters are not MVP requirements.

## 19. Testing Strategy

The architecture requires testing at multiple contract boundaries:

- State-machine tests for valid and invalid transitions.
- Command tests for authorization, expected revision, idempotency, target resolution, and no-op behavior.
- Snapshot and journal atomicity tests, including injected persistence failure.
- Contract compatibility tests for TeachingAction and TeachingScene versions.
- Deterministic mathematics and curriculum provenance tests.
- AI malformed-output, repair, timeout, staleness, and late-result tests.
- Role-projection negative tests proving private fields cannot reach the display.
- Display-epoch and two-phase replacement tests.
- Reload, revision-gap, corruption, and snapshot-resynchronization tests.
- Offline allowlist, reconciliation, conflict, journal-limit, and no-silent-ink-loss tests.
- End-to-end classroom tests using a laptop, external monitor, mouse, and smartphone.
- Security tests for pairing replay, brute-force attempts, stale grants, stale epochs, and cross-session access.

AI behavior must be tested through structured fixtures and evaluation cases rather than relying only on live model responses.

## 20. Security and Privacy

- The display receives an independently built public projection, never a combined object with private fields hidden by the client.
- Pairing secrets and credentials do not enter snapshots, command journals, prepared packages, or ordinary logs.
- Commands are bound to session, actor, role, authority lineage, contract version, and applicable epoch.
- Numeric pairing fallback is short-lived and rate-limited.
- Old controller and display authority is explicitly fenced.
- Untrusted AI output cannot execute code or directly control the renderer.
- Public content requires visibility classification and applicable validation.
- Student identity collection is minimized and is not required for the core MVP.
- Raw classroom audio is not persisted by default.
- Recovery artifacts containing classroom ink or teacher-private information require explicit retention and deletion policy.

## 21. Strengths of the Selected Architecture

- Directly matches the backend-authoritative product decision.
- Gives each client one clear recovery object: the current role-specific snapshot.
- Avoids unbounded event replay during classroom recovery.
- Makes revision conflict and command ordering explicit.
- Supports reliable idempotent retry after uncertain network outcomes.
- Provides strong fencing for display replacement.
- Keeps AI generation private and atomic until validated publication.
- Supports constrained offline continuity without granting clients canonical authority.
- Keeps teacher-private and learner-visible data boundaries explicit.
- Can start with low deployment and operational complexity.
- Leaves room for later event export, analytics projections, or service extraction without requiring them in the MVP.

## 22. Weaknesses and Risks

### 22.1 Snapshot Growth

The canonical snapshot may become large as scenes and annotations accumulate. The model must use stable references and bounded embedded state without weakening full-snapshot recovery semantics.

### 22.2 Command and Snapshot Coupling

Every command handler must correctly calculate a complete next state. Weak contract discipline could create divergent projections or invalid snapshots.

### 22.3 Private Revision Gaps

A public display may observe revision jumps caused by private mutations. Client recovery logic must understand that a global revision gap does not necessarily imply missing public content.

### 22.4 Offline Reconciliation

Ink, reveal state, and navigation conflicts can be subtle. The offline command set must remain narrow, explicit, and testable. Silent merge heuristics are prohibited.

### 22.5 Split-Brain Physical Display

Epoch fencing prevents an old display from changing canonical state but cannot remotely stop a fully offline screen from continuing to show cached material.

### 22.6 Async AI Staleness

Long-running generation may finish after scene navigation, pause, replacement, or termination. Dependency fingerprints and publication-time revalidation are mandatory.

### 22.7 Journal Misuse

The ordered command journal could be incorrectly expanded into an undeclared event-sourcing system. Normal session recovery must continue to use snapshots unless a later ADR explicitly changes the architecture.

### 22.8 Premature Distribution

Treating logical components as mandatory independent services would increase failure modes and operational cost. Deployment boundaries require later approval.

## 23. Conditions of Approval

The architecture is locked subject to all ten conditions below. Each is a mandatory architectural invariant.

### Condition 1 — Backend-Authoritative State

The backend is the sole authority for classroom-session state. Controller and display clients submit commands and consume projections; they never declare a snapshot canonical.

### Condition 2 — Atomic Snapshot and Ordered Journal

Every revision-producing command must atomically commit one complete canonical snapshot and one ordered command-journal entry. Partial commit is prohibited.

### Condition 3 — Monotonic Revision and Idempotent Commands

Every canonical mutation increments the session revision exactly once. Duplicate, rejected, read-only, heartbeat, and defined no-op operations do not create a new revision. Mutation commands must have stable idempotency semantics.

### Condition 4 — Single Writable Display with Epoch Fencing

At most one display has mutation authority. Initial activation and each replacement or revocation use a monotonic display epoch. Old-epoch commands and journals cannot mutate canonical state.

### Condition 5 — Contract-First Structured Rendering

Controller, display, backend, AI, curriculum, and validation boundaries use versioned structured contracts. `TeachingAction` and `TeachingScene` are semantic contracts. Arbitrary AI-generated HTML or executable renderer content is prohibited.

### Condition 6 — Atomic AI Scene Publication

AI produces private candidates, not public state. The last valid scene remains visible during generation, repair, validation, timeout, and approval. A new scene becomes public only through one complete atomic commit.

### Condition 7 — Deterministic Mathematics Validation

Learner-visible mathematical claims and transformations requiring validation must pass a deterministic mathematics boundary before publication. The LLM cannot self-certify correctness.

### Condition 8 — Controlled Curriculum Grounding

Curriculum-sensitive behavior must use pinned, controlled, versioned source data with traceable provenance. Uncontrolled model recollection is not curriculum authority.

### Condition 9 — Prepared-Lesson Cache and Safe Degradation

The active display must verify the prepared-lesson package before classroom start. During temporary connectivity loss, only a narrow allowlist of local actions may execute provisionally. Reconnection reconciles typed operations and restores a full authoritative snapshot. Offline ink is never silently lost.

### Condition 10 — Privacy and Role Isolation

Teacher-private, learner-visible, and system-only state must be projected independently. The display must never receive private teacher data, pairing secrets, credentials, raw audio, or internal AI material. Student data collection and audio retention are minimized by default.

## 24. Rejected Alternative 2 — Event-Sourced Session Core

### 24.1 Architecture

```text
Controller / Display commands
            │
            ▼
     Command handlers
            │
            ▼
   Append-only event stream
      ┌─────┼─────────┐
      ▼     ▼         ▼
 Session  Teacher   Display
projection projection projection
```

The authoritative record would be a complete domain-event stream. Current snapshots and role projections would be derived by replay or maintained as secondary materialized views.

### 24.2 Strengths

- Complete history of state evolution.
- Strong fit for audit, analytics, temporal queries, and future projection models.
- Natural integration point for independently built read models.
- Potentially powerful debugging and session-replay capabilities.

### 24.3 Weaknesses

- Event schema design and evolution become foundational MVP concerns.
- Rebuild, projection lag, replay compatibility, and snapshot cadence add complexity.
- Offline reconciliation must reason against event history as well as current state.
- Correctly separating commands, events, AI workflow events, public projections, and audit records requires substantial discipline.
- Recovery behavior is less direct than fetching one authoritative current snapshot.

### 24.4 Risks

- Event history may accidentally become coupled to current contract representations.
- A bad historical event or migration can impair reconstruction.
- Projection consistency and operational diagnosis require additional tooling.
- The team may over-invest in audit infrastructure before validating classroom behavior.

### 24.5 Rejection Reason

The option is technically viable but exceeds the MVP’s required operational and development complexity. Pendago needs auditability and ordering, but not full event replay as the primary source of truth.

It would be reconsidered if temporal reconstruction, many independent projections, regulatory audit, or high-volume downstream processing become dominant requirements.

## 25. Rejected Alternative 3 — Shared Realtime Document / CRDT Core

### 25.1 Architecture

```text
Controller replica ◀──── realtime operations ────▶ Display replica
        │                                             │
        └──────────────▶ shared document ◀────────────┘
                               │
                               ▼
                    Backend validation gateway
```

Controller, display, and backend would maintain convergent document replicas. Scene, reveal, navigation, or annotation changes would be represented as mergeable operations.

### 25.2 Strengths

- Strong support for collaborative editing and intermittent connectivity.
- Natural merging for some annotation operations.
- Low-latency local responsiveness.
- Potential future fit for multi-user canvases and student collaboration.

### 25.3 Weaknesses

- Convergence does not guarantee semantic validity or pedagogical correctness.
- Atomic scene publication and approval are unnatural in a continuously merging document.
- Backend authority must be reintroduced through complex validation and rejection rules.
- Curriculum, mathematics, and privacy constraints are not commutative document concerns.
- Navigation, reveal, assessment, display replacement, and AI candidate publication have ordering semantics that should not be silently merged.

### 25.4 Risks

- Invalid or private content could propagate before authoritative rejection.
- Teacher and display replicas could converge technically while violating classroom intent.
- Stale displays may continue producing operations after replacement.
- Conflict-resolution rules may become product behavior without explicit teacher control.
- Testing the full operation matrix would be disproportionately complex for MVP.

### 25.5 Rejection Reason

The option conflicts with the strongest product constraint: backend-authoritative, atomic, validated classroom state. A shared document model optimizes collaborative convergence, while Pendago’s MVP optimizes teacher control, safe publication, deterministic validation, and reliable recovery.

CRDT techniques may later be considered for a narrowly bounded annotation subsystem, but not as the authoritative classroom-session model without a new ADR.

## 27. Why Option 1 Was Selected

Option 1 provides the strongest balance across the approved priorities:

1. It has the clearest backend-authoritative state model.
2. It makes classroom recovery deterministic and understandable.
3. It supports atomic AI publication and deterministic validation without distributed merge ambiguity.
4. It enables safe degraded operation through a deliberately narrow provisional journal.
5. It supports display replacement through an explicit fencing epoch.
6. It keeps teacher-private and learner-visible state separate by construction.
7. It is simpler to develop, deploy, test, and operate than full event sourcing or a shared-document core.
8. It remains extensible: later analytics streams, event exports, additional projections, or bounded collaborative subsystems can be added without changing the initial source of truth.

Option 1 must be rejected or superseded only if a later approved requirement makes one or more of the following dominant:

- full historical reconstruction from domain events;
- many independently rebuilt projections;
- unconstrained multi-writer collaboration;
- offline-first creation without prior preparation;
- direct student-device collaboration as a core session primitive.

Any such change requires an explicit ADR and impact analysis against the locked product-discovery documents and the ten Conditions of Approval.
