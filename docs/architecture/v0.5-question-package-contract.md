## 1. Purpose

This specification defines Pendago `QuestionPackage` V0.1 as the canonical, internally consistent package for generated mathematical questions.

`QuestionPackage` is the validated semantic unit that binds together a question, its canonical answer, permitted equivalent answers, solution steps, hint ladder, explanation, difficulty metadata, curriculum mapping, representation data, misconception metadata, validation evidence, and provenance.

The package is produced as structured data and becomes learner-visible only through the `TeachingScene` and `TeachingAction` boundaries defined in V0.3 and V0.4. The LLM MAY propose a `QuestionPackage`, but it MUST NOT determine mathematical correctness, curriculum authority, or public reveal state.

This document does not define:

- frontend, backend, persistence, realtime, task-processing, AI-provider, container, cloud, or deployment technologies;
- serialization formats or transport protocols;
- framework manifests or production code;
- a math engine implementation;
- a complete curriculum dataset format;
- exact difficulty formulas or threshold values;
- exact retention durations or timeout values;
- exact mathematics-domain coverage.

## 2. Normative Language

The terms **MUST**, **MUST NOT**, **REQUIRED**, **SHOULD**, **SHOULD NOT**, and **MAY** are normative.

The **Session Core** is the backend authoritative command processor. **Publication** is the single atomic canonical mutation that makes a validated package's public question content visible. **Reveal** is a deterministic change to absolute reveal state for an existing protected package element.

### 4.1 Contract Versioning

- `QuestionPackage` versions are semantic and monotonic.
- Every package carries its contract version.
- Unknown or unsupported versions MUST fail closed before processing, rendering, or caching.
- Additive optional fields MAY be introduced in a backward-compatible minor version.
- Breaking changes include removing or renaming a required field, changing a field's type or cardinality, repurposing an enum value, or changing visibility/reveal semantics.
- A deprecated field MUST document its removal version and MUST NOT be silently reinterpreted.
- Prepared-cache packages MUST be migrated or invalidated when the package contract, curriculum version, or required validator versions change.

### 5.2 Field Definitions

#### `contractName`

- **Meaning:** Identifies the boundary contract as `QuestionPackage`.
- **Required/optional:** Required.
- **Producer:** Package producer.
- **Consumer:** Session Core and renderer compatibility layers.
- **Validation:** MUST equal the fixed value `QuestionPackage`.
- **Security/privacy:** Prevents type confusion with `TeachingScene` or `TeachingAction`.
- **Lifecycle:** Immutable for the lifetime of the contract version.

#### `contractVersion`

- **Meaning:** The semantic version of the `QuestionPackage` contract.
- **Required/optional:** Required.
- **Producer:** Package producer.
- **Consumer:** Session Core and renderer compatibility layers.
- **Validation:** MUST be a supported version. Version `0.1` is defined as supported.
- **Security/privacy:** Unsupported versions MUST fail closed.
- **Lifecycle:** Fixed per package.

#### `packageId`

- **Meaning:** A stable opaque identity for the package.
- **Required/optional:** Required.
- **Producer:** Package producer or Session Core.
- **Consumer:** Renderer, cache, reveal, annotation, and provenance references.
- **Validation:** MUST be non-empty, bounded, and unique within the lesson/package scope. MUST NOT be parsed as a number or path.
- **Security/privacy:** Identity is not authority; references resolve against canonical state.
- **Lifecycle:** Stable from creation through prepared caching and publication.

#### `packageRevision`

- **Meaning:** The canonical revision at which the package became authoritative.
- **Required/optional:** Required.
- **Producer:** Session Core.
- **Consumer:** Renderer, cache, and projections.
- **Validation:** MUST be the session revision at publication, or a package-stable revision for prepared content.
- **Security/privacy:** Used for staleness checks and cache migration.
- **Lifecycle:** Immutable for a published package; a repair or regeneration produces a new package identity or explicitly versioned successor.

#### `question`

- **Meaning:** The learner-facing question text and required public semantic content.
- **Required/optional:** Required.
- **Producer:** Package producer.
- **Consumer:** Renderer and semantic validation.
- **Validation:** MUST be structured text or validated mathematics; MUST NOT contain arbitrary HTML, CSS, scripts, or executable content.
- **Security/privacy:** The only part of the package that is public by default before reveal authorization.
- **Lifecycle:** Fixed after publication; a question edit is a new package version.

#### `canonicalAnswer`

- **Meaning:** The single deterministic correct answer for supported mathematics domains.
- **Required/optional:** Required.
- **Producer:** Package producer with mandatory deterministic-validator certification.
- **Consumer:** Validation, teacher-private projection, and reveal.
- **Validation:** MUST be deterministic where the domain supports it. MUST NOT be the LLM's uncertified assertion.
- **Security/privacy:** Protected content; hidden by default and never projected publicly before reveal authorization.
- **Lifecycle:** Fixed after validation; changing it invalidates the package or produces a new version.

#### `equivalentAnswers`

- **Meaning:** Deterministic answers that are mathematically equivalent to the canonical answer.
- **Required/optional:** Conditional; REQUIRED when a supported domain defines equivalent representations.
- **Producer:** Package producer with deterministic-validator certification.
- **Consumer:** Validation, teacher-private projection, and future assessment equivalence.
- **Validation:** Every entry MUST be proven equivalent by a deterministic validator. An entry without proof is excluded.
- **Security/privacy:** Protected content; not public before reveal.
- **Lifecycle:** Bounded in size; fixed after validation.

#### `solutionSteps`

- **Meaning:** The ordered deterministic solution progression.
- **Required/optional:** Required.
- **Producer:** Package producer with deterministic step validation.
- **Consumer:** Renderer reveal and diagnostics.
- **Validation:** MUST be ordered, non-empty, internally consistent with the canonical answer, and deterministically validated for each step where applicable.
- **Security/privacy:** Protected content; each step is reveal-authorized independently or in sequence.
- **Lifecycle:** Fixed after publication; reveal state changes through canonical actions.

#### `hintLevel1`

- **Meaning:** The first progressive hint.
- **Required/optional:** Conditional; REQUIRED when a hint ladder is produced.
- **Producer:** Package producer.
- **Consumer:** Renderer reveal and private teacher projection.
- **Validation:** MUST not leak the canonical answer or later solution steps prematurely.
- **Security/privacy:** Protected content; hidden by default.
- **Lifecycle:** Fixed after publication.

#### `hintLevel2`

- **Meaning:** The second progressive hint.
- **Required/optional:** Conditional; REQUIRED when a two-level hint ladder is produced.
- **Producer:** Package producer.
- **Consumer:** Renderer reveal and private teacher projection.
- **Validation:** MUST follow `hintLevel1` in difficulty/disclosure and MUST not leak the answer.
- **Security/privacy:** Protected content; hidden by default.
- **Lifecycle:** Fixed after publication.

#### `explanation`

- **Meaning:** The pedagogical explanation or rationale for the answer.
- **Required/optional:** Conditional.
- **Producer:** Package producer.
- **Consumer:** Renderer reveal and private teacher projection.
- **Validation:** MUST be consistent with the canonical answer and validated mathematics where applicable.
- **Security/privacy:** Protected content; hidden by default.
- **Lifecycle:** Fixed after publication.

#### `difficulty`

- **Meaning:** A structured, multidimensional difficulty model.
- **Required/optional:** Required.
- **Producer:** Package producer.
- **Consumer:** Policy, diagnostics, and private teacher UI.
- **Validation:** MUST use the multidimensional dimensions in Section 10. A simplified public/teacher label is optional.
- **Security/privacy:** Metadata; MAY be visible to the teacher but is not learner-visible unless product policy permits.
- **Lifecycle:** Fixed after publication.

#### `curriculum`

- **Meaning:** Controlled curriculum mapping and pinned curriculum version.
- **Required/optional:** Conditional; REQUIRED when curriculum alignment is enabled for the lesson.
- **Producer:** Curriculum grounding boundary.
- **Consumer:** Curriculum validation and diagnostics.
- **Validation:** MUST reference a controlled, versioned curriculum source and a topic/concept mapping. Model recollection is not authority.
- **Security/privacy:** Public provenance is minimal; internal mapping detail is system-only.
- **Lifecycle:** Pinned at package creation; changing curriculum version invalidates prepared packages.

#### `representation`

- **Meaning:** Structured renderer-safe representation data for the question, answer, or steps.
- **Required/optional:** Conditional.
- **Producer:** Package producer.
- **Consumer:** Renderer and representation validation.
- **Validation:** MUST use supported `TeachingScene` object families and MUST NOT contain renderer code.
- **Security/privacy:** Representation data is public only where it represents public question content; protected portions are reveal-gated.
- **Lifecycle:** Fixed after publication.

#### `misconceptions`

- **Meaning:** Structured metadata describing common error patterns associated with the concept.
- **Required/optional:** Conditional.
- **Producer:** Package producer with curriculum/misconception evidence.
- **Consumer:** Private teacher diagnostics and assessment results.
- **Validation:** MUST NOT claim an actual student misconception without actual response evidence. It records potential patterns, not individual claims.
- **Security/privacy:** Teacher-private by default; NEVER projected publicly.
- **Lifecycle:** Fixed after publication.

#### `validation`

- **Meaning:** Deterministic and semantic validation evidence.
- **Required/optional:** Required.
- **Producer:** Validation boundary.
- **Consumer:** Publication gate, diagnostics, and renderer readiness.
- **Validation:** MUST record the validation outcome and applicable validator versions. Unsupported or inconclusive results MUST be recorded as not verified.
- **Security/privacy:** Public projection includes only a minimal verified marker when product design requires it; detailed evidence is system-only.
- **Lifecycle:** Computed before publication; immutable after acceptance.

#### `provenance`

- **Meaning:** Traceable origin of the package content.
- **Required/optional:** Required.
- **Producer:** Package producer.
- **Consumer:** Diagnostics, audit, and curriculum validation.
- **Validation:** MUST record generation source and applicable source classification without raw AI material.
- **Security/privacy:** Internal AI reasoning and intermediate fragments are system-only.
- **Lifecycle:** Immutable for the lifetime of the package.

#### `reveal`

- **Meaning:** The canonical absolute reveal state for protected package elements.
- **Required/optional:** Required.
- **Producer:** Session Core.
- **Consumer:** Renderer and TeachingAction `PRESENTATION_CONTROL`.
- **Validation:** MUST reference existing protected elements by stable identity with explicit visible/hidden state.
- **Security/privacy:** Reveal state is authoritative and cannot be bypassed by renderer-side hiding.
- **Lifecycle:** Changed only by canonical reveal actions; offline changes reconcile through the V0.2 provisional journal.

#### `integrity`

- **Meaning:** A digest marker binding the package's exact content and contract version.
- **Required/optional:** Required.
- **Producer:** Package producer or Session Core.
- **Consumer:** Renderer, prepared cache, and projections.
- **Validation:** MUST be recomputed and verified before render or cache acceptance.
- **Security/privacy:** Prevents tampered or corrupted prepared packages from rendering.
- **Lifecycle:** Fixed for the package's exact content.

#### `createdAt`

- **Meaning:** The package's creation timestamp.
- **Required/optional:** Required.
- **Producer:** Package producer.
- **Consumer:** Diagnostics and cache.
- **Validation:** MUST be a valid timestamp.
- **Security/privacy:** Public metadata only.
- **Lifecycle:** Fixed at creation.

#### `expiresAt`

- **Meaning:** Optional expiry for cache or approval-lifetime policy.
- **Required/optional:** Conditional.
- **Producer:** Package producer or Session Core.
- **Consumer:** Cache, approval, and diagnostics.
- **Validation:** MUST be a valid timestamp when present.
- **Security/privacy:** Expiry is policy metadata; no numeric duration is locked here.
- **Lifecycle:** Evaluated by cache and approval policy.

## 6. Question Content

### 6.1 Public Question Content

The public question content MUST:

- be structured text, validated mathematics, or a supported renderer object;
- contain no answer, no hidden solution hint, and no protected private content;
- be complete and self-contained for learners;
- declare its primary natural language;
- be deterministic and stable after publication.

### 6.2 Answer-First Consistency

- The question and canonical answer MUST be generated or selected together as one package candidate.
- A question MUST NOT be published without a validated canonical answer.
- Question wording, answer, solution steps, hints, explanation, and representation MUST be mutually consistent.

## 7. Canonical Answer

- The canonical answer is the authoritative deterministic correct answer for supported mathematics domains.
- The LLM MAY propose the answer text, but a deterministic validator MUST certify correctness.
- The canonical answer is protected content and is hidden by default.
- The public question projection MUST NOT embed the canonical answer as visible text.
- Where deterministic equivalence is defined, `equivalentAnswers` MAY record proven alternatives.

## 8. Permitted Equivalent Answers

- Equivalent answers are permitted only when a deterministic validator proves mathematical equivalence to the canonical answer.
- Unproven equivalent answers MUST NOT be included.
- Equivalent-answer sets MUST be bounded in size.
- Equivalent answers follow the same public/private and reveal semantics as the canonical answer.

## 9. Ordered Solution Steps

- Solution steps MUST be an ordered, non-empty sequence.
- Each step MUST be stable and independently addressable for reveal.
- Deterministic steps MUST carry validation evidence where the domain supports validation.
- Steps MUST progress from the question toward the canonical answer without contradiction.
- A step MUST NOT leak a later protected step or answer by embedding it as public question content.

## 10. Hint Ladder

- `hintLevel1` MUST be less disclosing than `hintLevel2`.
- `hintLevel2` MUST be less disclosing than solution steps and the canonical answer.
- Hints MUST reference the same concept, topic, and difficulty.
- Prepared hints are deterministic and MUST NOT require a new AI generation request to reveal.
- Hint content is protected and hidden by default.

## 11. Explanation

- The explanation MUST be consistent with the canonical answer and solution steps.
- Mathematical claims within the explanation MUST pass deterministic validation where supported.
- The explanation is protected content and is hidden by default.

## 12. Difficulty Model

The difficulty model is multidimensional and conceptually includes:

- conceptual complexity;
- computational complexity;
- number of solution steps;
- language complexity;
- abstraction level.

Rules:

- The exact formula and dimension weights are NOT locked by this specification.
- A simplified teacher-facing scale MAY use `Mudah`, `Sedang`, and `Sulit`.
- Difficulty is internal metadata; it MUST NOT drive deterministic correctness or replace validation.

## 13. Curriculum Mapping and Pinned Curriculum Version

- Curriculum-sensitive packages reference the controlled, versioned curriculum source pinned by the lesson.
- A package MUST include topic/concept mapping consistent with that pinned version.
- The LLM MUST NOT act as curriculum authority.
- A teacher curriculum override disables required curriculum mapping but MUST NOT disable deterministic math validation.
- Curriculum version changes invalidate prepared packages bound to the previous version.

## 14. Representation Data

- Representation data MUST use supported `TeachingScene` object families.
- It MUST NOT contain arbitrary HTML, CSS, scripts, executable code, component names, or renderer instructions.
- Representations MAY include a validated visual representation when the concept supports it.
- Default representation selection is renderer-safe; a teacher request for another representation creates a new validated representation, not arbitrary layout.

## 15. Misconception Metadata

- Misconception metadata records potential common error patterns associated with the concept.
- It MUST NOT assert that a specific student has a misconception without actual response evidence.
- It is teacher-private and MUST NEVER be part of the public classroom projection.
- Assessment results MAY reference misconception metadata privately.

## 16. Validation Evidence

`validation` MUST record:

- deterministic math validation outcome;
- semantic consistency validation outcome;
- applicable validator identities and versions;
- a status of `NOT_VALIDATED`, `VALIDATING`, `VERIFIED`, `INVALID`, `UNSUPPORTED`, or `INCONCLUSIVE`;
- a traceable reference to the evidence without exposing internal diagnostic detail publicly.

Rules:

- `NOT_VALIDATED` means validation has not started.
- `VALIDATING` means validation is in progress.
- `VERIFIED` means all applicable deterministic and semantic checks passed.
- `INVALID` means at least one required validation failed.
- `UNSUPPORTED` means the domain has no deterministic validator.
- `INCONCLUSIVE` means validation could not establish correctness.
- `NOT_VALIDATED`, `VALIDATING`, `INVALID`, `UNSUPPORTED`, and `INCONCLUSIVE` MUST NOT be represented as verified and MUST NOT be publicly published.

## 17. Provenance

Provenance records:

- generation source classification;
- originating TeachingAction or preparation workflow where applicable;
- pinned lesson and curriculum versions;
- validator identities and versions;
- no raw audio, raw AI prompts, or intermediate candidate fragments.

## 18. Public/Private Projection Rules

### 18.1 Resolved V0.4 Deferred Decision

**Decision:** Option B is adopted.

**Option B definition:** Embed only currently public content and reference protected content.

### 18.2 Projection Model

| Content | Default public projection | Reveal-authorized public projection | Teacher-private projection | System-only |
|---|---|---|---|---|
| `question` | Included | Included | Included | Not applicable |
| `canonicalAnswer` | Excluded | Included only after reveal | Included | Not applicable |
| `equivalentAnswers` | Excluded | Included only after reveal | Included | Not applicable |
| `solutionSteps` | Excluded | Included step-by-step after reveal | Included | Not applicable |
| `hintLevel1` | Excluded | Included only after reveal | Included | Not applicable |
| `hintLevel2` | Excluded | Included only after reveal | Included | Not applicable |
| `explanation` | Excluded | Included only after reveal | Included | Not applicable |
| `misconceptions` | Excluded always | Excluded always | Included | Diagnostic evidence |
| Detailed validation evidence | Excluded | Excluded | Minimal when product requires | Included |
| Provenance internals | Excluded | Excluded | Minimal when product requires | Included |
| Integrity metadata | Operational only | Operational only | Operational only | Included |

### 18.3 Rules

- The classroom display receives an independently built public projection.
- The renderer MUST NOT receive protected content merely to hide it client-side.
- A reveal authorization is a canonical `PRESENTATION_CONTROL` change before the content enters the public projection.
- Private answers or solutions MUST NOT leak into the public classroom projection before reveal authorization.
- For degraded operation, a verified prepared package MAY store protected reveal resources in a display-local protected cache boundary. Those resources are not part of the active renderer input and may be materialized only after a canonical or offline-provisional reveal authorization.
- Protected reveal resources are pre-authorized potential public lesson content. They MUST NOT include teacher-private `ASK` or `ASSESS` results, misconception diagnostics, internal validation details, or AI reasoning.

## 19. Reveal Semantics

- Reveal state is deterministic and absolute: visible or hidden.
- Every protected element has a stable identity.
- Prepared reveal sequences define an explicit ordering: hint 1, hint 2, solution steps in order, explanation, then answer.
- Reveal changes are canonical mutations through `PRESENTATION_CONTROL`.
- Revealing prepared content normally MUST NOT require a new AI generation request.
- Reveal transitions to an already-satisfied state are defined no-ops.
- Offline reveal uses absolute desired states and reconciles through the V0.2 provisional journal.

## 20. TeachingScene Integration

- A `QUESTION` scene references or contains the public portion of the `QuestionPackage`.
- The scene's `revealGroups` reference protected package elements by stable identity.
- The scene's `objects` include only renderer-safe public content and representation data.
- The scene and package MUST share the same lesson, curriculum, and package identity bindings.
- The scene MUST NOT embed the canonical answer or protected solution steps as visible public objects.

## 21. TeachingAction Integration

- `GENERATE` actions create a package candidate through an async workflow; the public scene remains unchanged until publication.
- `PRESENTATION_CONTROL` actions change reveal state on existing stable package elements.
- `MODIFY` actions on a published package produce a new validated candidate; they do not mutate the published package in place.
- `ASSESS` actions MAY use the canonical and equivalent answers only in private teacher-facing results.
- `NAVIGATE` actions may move to the scene referencing the package.
- Offline reveal and navigation are allowlisted only for prepared package content.

## 22. Prepared-Lesson/Offline Requirements

A prepared package MUST include:

- immutable package identity and version;
- public question content;
- canonical answer;
- permitted equivalent answers;
- ordered solution steps;
- hint level 1 and hint level 2 when present;
- explanation when present;
- complete reveal data and default hidden state;
- representation data;
- curriculum version pinning where applicable;
- integrity metadata;
- renderer contract compatibility.

Rules:

- The display MUST NOT report classroom-ready when required package resources are missing.
- Protected answer, hint, solution, and explanation resources MUST be isolated from the active public renderer projection until reveal authorization.
- The renderer receives only the currently public materialized projection, even when the protected resources exist in the display-local prepared cache.
- Offline reveal and navigation operate on verified cached packages only.
- Online-only generation, modification, and assessment remain unavailable while degraded.
- Package integrity and curriculum/contract compatibility are verified before offline use.

## 23. AI Generation Boundary

- The AI boundary MAY propose the package structure, wording, explanation, difficulty metadata, and representation suggestions.
- The AI boundary MUST NOT certify mathematical correctness.
- The AI boundary MUST NOT directly publish a package.
- Generation is asynchronous and bounded; one public-scene-affecting workflow at a time per V0.2.
- Intermediate fragments, raw prompts, and model reasoning never enter canonical state or the public projection.

## 24. Deterministic Mathematics Validation

### 24.1 Supported Domains

- Deterministic validation applies wherever a controlled math validator exists.
- The exact domain coverage is NOT enumerated here; coverage is a controlled capability advertised by the validator boundary.

### 24.2 Validation Obligations

- Validate the canonical answer.
- Validate mathematical equivalence of any permitted equivalent answers.
- Validate solution-step consistency where deterministic.
- Validate representation consistency where applicable.
- Record validator versions and evidence.

### 24.3 Authority Rule

The LLM MAY propose mathematics but MUST NOT certify correctness. The validator decides deterministic correctness.

## 25. Repair/Regenerate/Reject Policy

### 25.1 Deterministic Repair

- When a deterministic validator can safely repair a single malformed or inconsistent element, deterministic repair is preferred.
- Repair MUST NOT silently change the question meaning, canonical answer, or public intent.
- A repaired package is a new candidate with a new integrity digest and revalidation.

### 25.2 Regeneration

- Regeneration is bounded.
- The exact attempt count is not locked by this specification.
- Each regeneration produces a new candidate identity/hash and invalidates prior approval.

### 25.3 Rejection

- If repair or bounded regeneration fails, the package MUST be rejected and reported privately.
- An invalid package MUST NOT be publicly published.
- The last stable public scene remains unchanged.

## 26. Unsupported/Inconclusive Validation Behavior

- `UNSUPPORTED` or `INCONCLUSIVE` results MUST NOT be represented as `VERIFIED`.
- Such packages MUST NOT be publicly published for learner-facing mathematics unless a later approved product decision explicitly permits a clearly labeled non-verified pedagogical presentation.
- The teacher receives a private, non-technical notice.
- System diagnostics retain the evidence without exposing raw AI material.

## 27. Contract Evolution

- `QuestionPackage` versions are semantic and monotonic.
- Additive optional fields MAY be introduced in backward-compatible minor versions.
- Breaking changes require a new major version and migration planning.
- Object families and reveal semantics MUST remain aligned with the `TeachingScene` contract.
- Prepared-cache packages MUST be migrated or invalidated on breaking contract, curriculum, renderer, or validator changes.

## 29. Examples and Counterexamples

### 29.1 Valid Fraction Addition Package

Question: `1/2 + 1/3 = ...`. Canonical answer `5/6`. Equivalent answers include `10/12` only if deterministically proven equivalent. Solution steps show common-denominator transformation. Hint 1 references denominator relationship; hint 2 references equivalent fractions. Validation status `VERIFIED`.

### 29.2 Valid Progressive Hint Package

Question asks for the area of a rectangle. Hint 1 recalls the area formula concept; hint 2 applies dimensions; solution step 1 substitutes values; the answer is hidden until final reveal.

### 29.3 Candidate Awaiting Validation

A proposed package has `validation` status `INCONCLUSIVE`. It is not published; the current stable scene remains visible.

### 29.4 Rejected Invalid Mathematics

An LLM proposes the canonical answer `1/2 + 1/3 = 2/5`. Deterministic validation fails. The package is not published and is reported privately.

### 29.5 Rejected Private-Answer Leakage

A `QUESTION` scene embeds the canonical answer in public question text. It is rejected as `UNSAFE_VISIBILITY`.

### 29.6 Rejected Unproven Equivalent Answer

A package lists `10/12` as an equivalent answer without equivalence proof. The unproven entry is excluded or the package is rejected, depending on whether the inconsistency breaks the rest of the package.

### 29.7 Prepared Offline Package

A prepared fraction package includes public question content, protected reveal data, curriculum version, validator evidence, and integrity metadata. The display verifies integrity and completeness before classroom-ready.

### 29.8 Misconception Metadata Used Privately

An assessment of `1/2 + 1/3 = 2/5` privately suggests the misconception of adding numerators and denominators directly. The misconception metadata never appears publicly.

## 30. Invariants

1. Question, answer, solution steps, hints, explanation, and representation form one internally consistent package.
2. The LLM may propose a package but MUST NOT determine mathematical correctness.
3. Mathematical correctness MUST be established by deterministic validation for supported domains.
4. Unsupported or inconclusive mathematics MUST NOT be represented as verified.
5. Invalid packages MUST NOT be publicly published.
6. Deterministic repair is preferred when safe.
7. Regeneration MUST be bounded.
8. Failed repair/regeneration rejects the package and reports it privately.
9. Prepared hints, solution steps, and answers normally reveal without another AI generation request.
10. Private answers or solutions MUST NOT leak into the public projection before reveal authorization.
11. Curriculum claims MUST reference controlled, versioned curriculum data.
12. The current stable scene survives package generation, validation, approval, failure, or timeout.
13. Package publication is atomic.
14. Prepared packages are integrity-checked before render or cache acceptance.
15. Unsupported contract, renderer, validator, or curriculum versions fail closed.

## 31. Testable Acceptance Criteria

### 31.1 Schema Conformance

1. A package missing a required field is rejected as `MALFORMED_PACKAGE`.
2. An unsupported `contractVersion` is rejected before processing.
3. Unknown fields are rejected or ignored only under a defined additive-version rule.

### 31.2 Internal Consistency

4. A package whose solution steps contradict its canonical answer is rejected.
5. A package whose hints leak the answer is rejected.
6. A package whose explanation contradicts its steps is rejected.

### 31.3 Deterministic Math Validation

7. A `VERIFIED` package has deterministic validator evidence.
8. An invalid math package is not published.
9. Unproven equivalent answers are excluded.
10. `UNSUPPORTED` or `INCONCLUSIVE` packages are not marked verified.

### 31.4 Repair and Regeneration

11. Deterministic repair is applied when safe and produces a new integrity digest.
12. Regeneration is bounded and invalidates prior approval.
13. Exhausted repair/regeneration rejects the package privately without changing the public scene.

### 31.5 Public/Private Isolation

14. Default public projection contains only the question content.
15. Protected content appears only after canonical reveal authorization.
16. The renderer never receives hidden protected content.
17. Misconception metadata never reaches the display.

### 31.6 Reveal Behavior

18. Prepared reveal requires no new AI call.
19. Reveal ordering follows the prepared sequence.
20. Revealing an already-visible element is a defined no-op.

### 31.7 TeachingScene and TeachingAction

21. A `QUESTION` scene references the package public content by stable identity.
22. `PRESENTATION_CONTROL` changes reveal state without regenerating the package.
23. `MODIFY` produces a new candidate rather than in-place mutation of a published package.

### 31.8 Prepared Cache and Offline

24. A prepared package missing required reveal data is not classroom-ready.
25. Integrity failure prevents render and cache acceptance.
26. Curriculum/contract/validator version changes invalidate affected prepared packages.

### 31.9 Contract Evolution

27. Unsupported package versions fail closed.
28. Breaking changes trigger prepared-cache migration or invalidation.

### 31.10 Regression Boundary

29. A previously verified package remains verifiable after validator-version changes only if the validator boundary declares compatibility; otherwise it is revalidated or invalidated.
30. A fixed invalid-equivalence regression case continues to be rejected after package-contract changes.

### 31.11 Evaluation and AI Regression Harness

The future evaluation harness MUST include versioned fixtures for:

- valid Grade 5 fraction packages;
- valid Grade 7 basic algebra and linear-equation packages;
- invalid canonical answers;
- invalid or unproven equivalent answers;
- inconsistent solution steps;
- hint and explanation answer leakage;
- curriculum version mismatch;
- public/private projection leakage;
- unsupported and inconclusive validator outcomes;
- deterministic repair success and failure;
- bounded regeneration exhaustion;
- prepared-cache integrity and reveal completeness.

Evaluation rules:

- Deterministic graders decide schema conformance, mathematical correctness, equivalence, step consistency, reveal references, integrity, and projection leakage.
- Model-based graders MAY evaluate wording clarity, pedagogical progression, and age appropriateness, but MUST NOT certify mathematical correctness.
- Human review is required for changes to difficulty policy, curriculum interpretation, unsupported-domain publication policy, or public-projection semantics.
- Every production defect involving an incorrect answer, invalid step, answer leakage, or validator bypass MUST add a permanent regression fixture.
- Evaluation baselines are versioned by QuestionPackage contract, curriculum version, validator versions, and renderer contract version.
- No numerical pass-rate target is locked by this architecture specification.

Additional acceptance criteria:

31. A deterministic invalid-answer fixture always fails regardless of LLM confidence or execution mode.
32. A public-projection leakage fixture always fails when protected answer, hint, solution, misconception, or diagnostic data appears before reveal authorization.
33. A previously fixed package inconsistency remains rejected after model, prompt, contract, or validator changes.
34. Model-based clarity evaluation cannot override a deterministic mathematical failure.
35. Prepared-cache fixtures prove every required protected reveal resource is complete and integrity-bound without entering the active renderer projection prematurely.

## 32. Decisions Requiring Product Approval

### 32.1 QuestionPackage Public Projection Option

**Question**
Which projection strategy should Pendago adopt for protected question-package content?

**Available options**

A. Embed all content and hide private portions client-side.
B. Embed only currently public content and reference protected content.
C. Keep the entire package server-side and expose projections only.

**Recommendation**
Option B.

**Rationale**
Option B preserves the backend-enforced `PUBLIC`/`PRIVATE_TEACHER` boundary and keeps prepared reveal data available offline. Hidden answers or solution steps may exist only inside an integrity-verified protected reveal cache and are not supplied to the active renderer until authorized. Option A violates the no-client-side-hiding rule by sending a combined render payload. Option C maximizes server-side control but would require online round-trips for every reveal, weakening prepared-lesson and degraded-connectivity behavior.

**Blocks V0.5 lock**
This decision is resolved in this specification as Option B. It does not block V0.5 lock, but changing it later requires an ADR or superseding specification.

### 32.2 Validator Domain Coverage

**Question**
Which mathematics domains receive a deterministic validator in MVP?

**Available options**

1. Prototype slices only: Grade 5 fractions and Grade 7 basic algebra/linear equations.
2. The full listed MVP scope: arithmetic, fractions, decimals, percentages, basic algebra, linear equations, basic geometry, perimeter, area, and basic angles.
3. A reduced teacher-selected subset.

**Recommendation**
Start with the prototype slices and expand validator coverage through a controlled capability-advertisement process; do not enumerate the complete MVP domain list as all validated until the validator boundary declares coverage.

**Rationale**
Product Discovery V0.4 identifies the two prototype slices for proving the architecture and separately lists later MVP scope. Claiming full validator coverage without a selected math engine would be an unsupported product assumption.

**Blocks V0.5 lock**
No. The validation boundary is domain-capability-driven; the package contract does not depend on a fixed domain list.

### 32.3 Difficulty Formula

**Question**
What exact formula or weights define the multidimensional difficulty model?

**Available options**

1. Defer any formula.
2. Use qualitative dimensions with no aggregate score.
3. Use a weighted numeric aggregate.
4. Use a fixed ordinal ladder.

**Recommendation**
Use qualitative dimensions with no locked aggregate score; optionally expose the simplified `Mudah`/`Sedang`/`Sulit` label.

**Rationale**
The product discovery model is multidimensional but does not lock weights or a formula. Inventing one now would be premature and could mislead generation or assessment behavior.

**Blocks V0.5 lock**
No. The field model is defined; the aggregation policy is deferred.

### 32.4 Repair and Regeneration Bound

**Question**
What numeric bound limits deterministic repair and regeneration attempts?

**Available options**

1. Defer the number entirely.
2. One repair plus one regeneration.
3. A policy-configured bound.
4. Unbounded until success.

**Recommendation**
Use a policy-configured bound with a low default, and do not lock the number in V0.5.

**Rationale**
The requirement is that regeneration is bounded; the exact value is an operational policy that may need tuning and must not be silently invented.

**Blocks V0.5 lock**
No. The boundedness invariant is defined; the numeric value is deferred.

### 32.5 Non-Verified Pedagogical Presentation

**Question**
May an `UNSUPPORTED` or `INCONCLUSIVE` package ever be presented to learners with an explicit "not verified" label?

**Available options**

1. Never publish non-verified packages.
2. Publish only if teacher explicitly approves and a visible non-verified label is shown.
3. Publish as verified in supported domains only.

**Recommendation**
Never publish non-verified packages in MVP; require an explicit future product decision if labeled non-verified presentation becomes desirable.

**Rationale**
The locked rule is that invalid or unverified mathematics must not be represented as verified. A labeled non-verified path would be a product-policy change with learner-safety implications and needs separate approval.

**Blocks V0.5 lock**
No. The fail-closed default is defined; the optional future behavior is deferred.

### 32.6 Hint-Ladder Depth Policy

**Question**
How many hint levels and solution steps are expected for each package?

**Available options**

1. Exactly two hints and a fixed step count.
2. Up to two hints and a variable validated step count.
3. No hints for some question types.

**Recommendation**
Allow up to two hints and a variable validated step count, with hint presence conditional on the package type.

**Rationale**
Product Discovery V0.4 specifies a hint ladder with Hint 1 and Hint 2 but does not lock that every question always has both hints or a fixed number of steps.

**Blocks V0.5 lock**
No. The conditional cardinality is defined.
