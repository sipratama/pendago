# Product Discovery V0.5 — Physical Classroom & Device Experience

**Status:** LOCKED  
**Locked:** 4 September 2026

## 1. Hardware levels

### Level 1 — Minimum full product

```text
Laptop / PC
+
Monitor / TV / Projector
+
Teacher Smartphone
+
Internet
```

This is considered a **full minimum product**, not a limited demo mode.

### Level 2 — Touch

```text
Laptop / PC
+
Touch-enabled display
+
Teacher Smartphone
```

### Level 3 — Interactive board

```text
Interactive Smart Board
+
Teacher Smartphone
```

Smart-board-specific hardware is not required for the product to be valuable.

## 2. Device responsibility

### Teacher smartphone

Owns teacher-facing functions:

- teacher authentication;
- class/lesson selection;
- push-to-talk;
- private answers;
- AI approvals;
- AI suggestions;
- teacher controls.

### Classroom display

Owns classroom-facing functions:

- TeachingScene rendering;
- digital ink;
- lesson navigation;
- local lesson cache;
- session recovery.

## 3. Pairing

Pairing supports:

- QR code;
- numeric code fallback.

Pairing is **per teaching session**, not permanently bound to the classroom computer.

## 4. Network topology

The product must **not** depend on same-Wi-Fi or local network discovery.

Supported examples:

```text
Phone → Mobile Data → Cloud
Laptop → School Wi-Fi → Cloud
```

or:

```text
Teacher Phone Hotspot
        ↓
Laptop
        ↓
Cloud
```

The network topology is intentionally flexible.

## 5. Teacher phone screen behavior

During an active teaching session, the app should request Screen Wake Lock where supported.

Fallback instructions should exist for devices/browsers that cannot keep the screen awake reliably.

## 6. Controller disconnect behavior

The classroom session does **not** stop if the teacher phone:

- enters background;
- loses connectivity;
- closes the browser;
- temporarily disconnects.

The classroom display remains active.

When the controller returns, it reconnects and restores current state.

## 7. Display reload/recovery

Browser reload or recoverable browser failure should automatically restore:

- active session;
- current TeachingScene;
- relevant annotations;
- lesson progress.

The user should see a short recovery state rather than lose the lesson.

## 8. Display switching

Simple reconnect/switch to a new classroom display is part of MVP.

Example:

1. Active session exists on teacher phone.
2. Teacher opens classroom page on another laptop/display.
3. Pair new display.
4. Restore current session state.

This also supports teachers moving between rooms.

## 9. Display resolution

Official minimum target:

> **1280 × 720**

Preferred:

- 1920 × 1080.

Lower resolutions such as 1024×768 may receive best-effort compatibility but are not the primary design target.

## 10. Classroom content density

If content does not fit comfortably:

> **Split the scene. Do not shrink typography until everything fits.**

Classroom readability is more important than maximizing information density.

Scene rules should favor:

- large typography;
- high contrast;
- one primary concept;
- one primary visual;
- limited answer options;
- progressive disclosure.

## 11. Fullscreen

Fullscreen is **strongly recommended but optional**.

The teacher should not be blocked from teaching if fullscreen is not used.

## 12. Digital Ink MVP

Locked toolset:

- Pen
- Highlighter
- Eraser
- Undo
- Redo
- Clear Ink

Do not expand MVP into a full drawing application.

## 13. Touch / stylus behavior

Target:

> **smart stylus behavior where available + explicit mode fallback**

Concept:

- stylus can default to writing;
- finger may interact/select where reliable;
- explicit Select/Draw mode remains the reliable fallback.

Advanced hardware behavior such as palm rejection is device-dependent and should not be universally promised.

## 14. Student board interaction

Students may walk to the board and write without:

- logging in;
- selecting a student profile;
- using a personal smartphone.

Teacher can then request:

> “Periksa jawaban ini.”

The relevant ink is interpreted and assessed.

## 15. Degraded offline mode

Prepared lesson must remain usable when internet temporarily fails.

### Online

- prepared lesson;
- navigation;
- digital ink;
- AI generation;
- voice command;
- live AI.

### Degraded

Available:

- prepared scenes;
- navigation;
- digital ink;
- existing hints;
- existing answers;
- existing solution steps.

Unavailable:

- new live AI generation;
- cloud speech/AI processing.

### Recovery

When connectivity returns:

1. reconnect;
2. synchronize state;
3. restore AI features.

This is part of MVP.

## 16. Prepared lesson cache

When the teacher starts teaching, the classroom client should have local access to prepared lesson data such as:

- lesson metadata;
- prepared scenes;
- question packages;
- hints;
- answers;
- solution steps;
- structured visual data.

This makes existing lesson navigation resilient to temporary internet failure.

## 17. AI generation stability

Live AI generation should be atomic from the classroom perspective.

```text
CURRENT STABLE SCENE
       ↓
Generate
       ↓
Validate
       ↓
Renderer-ready
       ↓
REPLACE / ADD NEW SCENE
```

Do not expose half-generated classroom content.

## 18. Manual fallback controls

Voice is a primary interaction but not the only interaction.

The teacher controller must retain manual controls for essential classroom actions such as:

- Previous
- Next
- Show Hint
- Show Answer
- Undo
- Clear Ink
- Stop AI Voice

The class must remain controllable when voice processing is unavailable.

## 19. Physical classroom baseline

The MVP must be developable and testable using:

```text
Developer laptop
+
ordinary monitor
+
mouse as stylus/touch simulation
+
smartphone as teacher controller
```

A smart board is required later for compatibility validation, not initial development.
